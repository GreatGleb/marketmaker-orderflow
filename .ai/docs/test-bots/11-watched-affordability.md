# Отбор watched_pair по доступности покупки

Изменение от 2026-09-17: отбор дополнен лимитом номинала покупки.
Состав рынка эксперимента меняется; статистику до/после применения фильтра
следует различать. Баланс симулятора, входы/выходы, плечо и комиссии не менялись.

## Пути записи

В `general/app/scripts/init_setup.py`, `main`, первоначальное заполнение
вызывает `seed_watched_pairs`, если список ещё пуст. Уже заполненный список
init пропускает; для применения нового фильтра нужна пересборка.
`general/app/workers/scripts/rebuild_watched_pairs.py`, `main`, вызывает
ту же функцию с `replace=True` каждые 24 часа, первый раз через сутки после
запуска воркера. CLI — `general/app/scripts/seed_watched_pairs.py`, `main`.

В этом же файле `rank_by_jumps` ранжирует локальную историю, а
`top_up_from_binance` и `rank_from_binance` добирают по суточному размаху.
На пустой истории `bootstrap` временно записывает кандидатов, затем
`watch_and_rank` ранжирует собранные тики. Во всех ветках бюджет проверяется
до среза рейтинга; порядок, пороги оборота и скачков сохранены.

Единственная действующая точка записи — `apply_watched_pairs`.
Она повторяет проверку после добавления закреплённых пар. При дополнении
списка, пустом результате и срабатывании защиты короткого топа старые пары
сохраняются **только если проходят фильтр**. Недоступные удаляются обычным
`delete(WatchedPair)`, включая закреплённые за активными ботами.
`general/app/crud/watched_pair.py`, `get_symbol_to_id_map`, только читает список.

## Расчёт и источники

Настройка `general/app/config.py`, `WATCHED_PAIR_MAX_BUY_NOTIONAL_USDT`,
имеет тип Decimal и дефолт `9`. Это стоимость позиции, не маржа.
Рынок остаётся Binance USDⓈ-M PERPETUAL в USDT/USDC. Проект использует
рыночное исполнение, в том числе условные рыночные входы:
`general/app/bots/binance_bot.py`, `create_orders`, `FUTURE_ORDER_TYPE_STOP_MARKET`.
Фильтр проверяет возможность обычной открывающей MARKET-покупки сейчас;
будущие цены активации условного ордера он не прогнозирует.

`general/app/services/watched_affordability.py`, `minimum_quantity`, находит
минимальное q, удовлетворяющее одновременно:

- границам minQty/maxQty и сеткам `(q - minQty) % stepSize == 0`
  из LOT_SIZE и MARKET_LOT_SIZE;
- `q × markPrice >= MIN_NOTIONAL.notional`;
- `q × max(askPrice, markPrice) × курс_котировки_в_USDT <= бюджет`.

Пересечение сеток считается в целых единицах Decimal-масштаба, без перебора
лотов; округление минимального количества только вверх. Если результат
дороже бюджета, пара исключается. Равенство разрешено, quantityPrecision
не заменяет шаг, плечо в расчёт не входит. Например, при цене 3000,
minQty=stepSize=0.001 и минимальном номинале 5 достаточно 0.002 монеты
на 6 USDT. При минимальном номинале 10 пара не проходит независимо от
низкой цены монеты.

`load_snapshot` получает общий exchangeInfo, futures bookTicker и
premiumIndex (mark price). Отдельный общий запрос spot ticker/24hr USDCUSDT (askPrice и closeTime)
нужен **только для курса пересчёта валют**, спотовые фильтры и цены базовых
монет не используются. USDC не считается равным USDT автоматически.
При отсутствии курса исключаются USDC-пары, USDT не зависят от него.

`seed_binance_data(data=...)` сохраняет уже полученный exchangeInfo;
`AssetExchangeSpecCrud.get_or_create` теперь обновляет существующую запись,
включая filters/status/orderTypes, не затрагивая ставки комиссии.
Схема БД не меняется. Старые строки БД не служат запасным источником
ограничений: у них нет достоверной отметки свежести спецификации.

`Snapshot.keep` и `check_purchase` исключают пары с отсутствующими,
некорректными, неположительными или бесконечными значениями, статусом
не TRADING, без MARKET, без необходимых фильтров. Время цены проверяется
по полям time/closeTime; максимум возраста — 60 секунд, допуск часов
в будущее — 5 секунд. Снимок ограничений живёт максимум 60 секунд с начала
загрузки; затем `affordable_symbols` обновляет его целиком. Длительный
bootstrap поэтому получает новый снимок. Запросов по каждой паре нет.
Причина каждого отказа пишется в лог с символом. При сетевом отказе нет
перехода на старые ограничения: пары без свежих данных исключаются,
вплоть до пустого списка.

Это проверка по текущему снимку: рыночное исполнение позднее может иметь
другую цену из-за движения рынка и проскальзывания. Проверка доступности
не изменяет механизм выставления/симуляции сделок.

Официальные источники Binance, сверены 2026-09-17:

- [USDⓈ-M filters](https://developers.binance.com/docs/derivatives/usds-margined-futures/common-definition),
  LOT_SIZE, MARKET_LOT_SIZE и MIN_NOTIONAL (для MARKET используется mark price).
- [USDⓈ-M market data](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data),
  Exchange Information, Symbol Order Book Ticker, Mark Price.
- [Spot market data](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/market),
  24hr ticker price change statistics, askPrice — исключительно курс USDCUSDT.

## Применение и потребители

После доставки кода перезапустить только процесс `rebuild_watched_pairs`,
чтобы суточный воркер загрузил новую реализацию (`general/supervisord.conf`,
`[program:rebuild_watched_pairs]`). Для применения
сразу, из корня проекта:

```bash
docker exec -it orderflow_general python -m app.scripts.seed_watched_pairs --replace
```

Для другого лимита задать `WATCHED_PAIR_MAX_BUY_NOTIONAL_USDT` в окружении
процесса. Ручной запуск с `docker exec -e` влияет только на этот прогон;
для суточного воркера настройка должна попадать в окружение контейнера.

Скрипт использует существующий `paused_simulator`: останавливает симулятор
на время операции и возвращает только ранее работавшие процессы. Под
симулятором, запущенным вручную, работать отказывается. Это штатное
поведение пересборки; во время разработки торговли не запускаем.

При изменении списка `restart_price_feed` перезапускает `symbols_history`:
для spot_ws подписка формируется при подключении, а ws/rest перечитывают
список на каждом сохранении (`watch_ws_and_save.py`, `save_filtered_assets`).
Дополнительный ручной перезапуск этих потребителей не нужен.
Вручную запущенный `order_book_listener` подписывается при подключении —
его нужно переподключить для новых пар; в штатном supervisord его нет.

Волатильный воркер выбирает из истории, а не напрямую из watched_pair;
старые тики и Redis-ключи не исчезают мгновенно. В штатных режимах сбора
только watched-пар цены исключённых символов перестают обновляться и
протухают по существующему TTL. При `MARKET_DATA_SPOT_SYMBOLS=all` сбор
спотовых цен шире watched_pair: этот фильтр списка не является запретом
сделок на уровне симулятора. Логику торговли задача не меняет.

Проверки: `general/tests/test_watched_affordability.py`, `main`, и
`general/tests/test_tradable_pairs.py`, `main`; обычные assert без БД и сети.
