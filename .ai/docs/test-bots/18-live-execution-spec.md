# 18. Требования к боевому исполнению на Binance USDⓈ-M

Дата: 2026-10-03. Источник — разбор ТЗ трейдера «Post-Impulse Short
Squeeze Reversal» (раздел 16 [15-orderflow-plan.md](15-orderflow-plan.md)).
Стратегия из того ТЗ закрыта, а ошибки в работе с API остаются ошибками
для любого следующего боевого бота. Трейдер подтвердил правки
2026-10-03.

Это требования, а не описание кода: нового боевого бота нет. Где
нынешний `general/app/bots/binance_bot.py` (копибот, в supervisord
выключен) с ними расходится — раздел 5.

---

## 1. Поток сделок: combined stream по парам

**Потока `!<arr>@aggTrade` на фьючерсах нет.** Общие для всего рынка
потоки есть только у `!ticker@arr`, `!miniTicker@arr`, `!bookTicker`,
`!markPrice@arr`, `!forceOrder@arr`. Сделки — только по паре:
`<symbol>@aggTrade`, имя пары в нижнем регистре.

* Адрес — `wss://fstream.binance.com/market/stream?streams=btcusdt@aggTrade/ethusdt@aggTrade/...`.
  Путь `/market` обязателен: с 2026-04-23 Binance разнёс потоки по
  `/public`, `/market`, `/private`, и по старому `/ws` соединение
  открывается, а данных нет. См. комментарий у `WS_URL` в
  `general/app/scripts/watch_ws_and_save.py` и пункт 29
  [08-gotchas.md](08-gotchas.md).
* **Пары раскладывать по нескольким сокетам.** Замер 8.11 плана 15:
  одно соединение отдаёт ~16–20 сообщений в секунду **независимо от
  числа стримов на нём** и рвётся каждые 25–50 с; те же стримы по
  пяти–десяти на сокет идут на полной скорости. Образец —
  `split_streams` в `general/app/scripts/order_book_listener.py`.
* Переподключение с нарастающей паузой, на каждом сокете своё. Биржа
  сама закрывает соединение через 24 часа — это штатный обрыв, не
  ошибка.
* Время события брать из поля `T` (время сделки), а не из времени
  получения: окно импульса в 2 с считается по бирже.

## 2. Количество: MARKET_LOT_SIZE, stepSize, MIN_NOTIONAL

`floor(POSITION_SIZE_USDT / price)` неверно: целое округление даёт 0 для
всего дороже $100 и теряет точность на остальных.

* Рыночный ордер проверяется по **двум** фильтрам количества —
  `LOT_SIZE` и `MARKET_LOT_SIZE`. Допустимое количество лежит на
  пересечении сеток `(q − minQty) % stepSize == 0`. Готовое пересечение —
  `quantity_grid` в `general/app/sub_services/logic/quantity_grid.py`
  (им пользуется симулятор) и `minimum_quantity` в
  `general/app/services/watched_affordability.py`.
* Количество под фиксированный бюджет округлять **вниз** до этой сетки:
  `origin + floor((budget / price − origin) / step) * step`. Только
  `Decimal`, не `float`.
* Отказаться от сигнала, если `qty < minQty` (любого из двух фильтров),
  `qty > maxQty` или `qty * price < MIN_NOTIONAL.notional`. Поднимать
  количество до минимума — значит торговать не тем размером, что в
  конфиге.
* Фильтры брать из `exchangeInfo` при старте и обновлять раз в сутки:
  биржа меняет их без предупреждения. Хранение — `AssetExchangeSpecCrud`
  (`extract_step_sizes` уже разбирает `MARKET_LOT_SIZE` и
  `MIN_NOTIONAL`).

## 3. Закрытие: reduceOnly и свой newClientOrderId

Повтор рыночного закрытия «каждые 500 мс до успеха» без проверки статуса
опасен: сетевая ошибка или таймаут не значат, что ордер не исполнился.
Второй Market Buy закрывает шорт дважды и открывает лонг.

* **Режим позиций — one-way.** В нём закрывающий ордер идёт с
  `reduceOnly=true`: биржа не даст ему открыть встречную позицию. В
  hedge-режиме (`dualSidePosition`) параметр `reduceOnly` биржа не
  принимает (ошибка -1106), там закрытие ограничено `positionSide`. Бот
  проверяет режим при старте и отказывается работать в чужом.
* **У каждого закрытия свой детерминированный `newClientOrderId`**,
  выведенный из позиции (например `<id позиции>-close`), один и тот же
  во всех повторах.
* Повтор после сетевой ошибки, таймаута или ответа 503 «execution status
  unknown»:
  1. запросить ордер по `origClientOrderId`;
  2. `FILLED` — закрыто, выйти;
  3. `NEW` / `PARTIALLY_FILLED` — ждать, не отправлять второй;
  4. -2013 «ордер не найден» — отправить заново с тем же id;
  5. -2022 «ReduceOnly rejected» — свериться с `positionRisk`: позиции
     нет — закрыто, есть — разобраться, а не повторять вслепую.

  Пауза 500 мс между итерациями, тревога в лог после N неудач.
* Отправка через асинхронный клиент. Синхронный вызов внутри
  корутины, как и `time.sleep`, останавливает весь цикл событий — вместе
  с потоком цен и таймерами выхода остальных позиций.

## 4. Защита на бирже

Тайм-стоп живёт в процессе: процесс упал — позиция осталась без выхода.
Сразу после входа ставить на бирже `STOP_MARKET` с `closePosition=true`
на аварийном уровне — не как часть стратегии, а на случай смерти
процесса. После штатного закрытия снимать его по своему
`clientOrderId`.

## 5. Где нынешний `binance_bot.py` расходится

Копибот выключен (`autostart=false` у `[program:binance_bot]`), поэтому
расхождения записаны, а не исправлены. Чинить их — отдельная задача
перед его включением.

| Требование | Как в `binance_bot.py` |
|---|---|
| Пересечение `LOT_SIZE` и `MARKET_LOT_SIZE` | Берёт только `lot_size` (`symbol_characteristics['lot_size']['stepSize']`) — и для рыночных ордеров тоже |
| Режим позиций | Принудительно hedge (`check_and_set_dual_mode`); `reduceOnly=True` в `delete_binance_order` поэтому всегда падает, и срабатывает запасная ветка без него |
| Свой id у закрытия | `deleting_order_id` необязателен: без него закрытие уходит без `newClientOrderId` и его статус потом не запросить |
| Проверка статуса перед повтором | Нет: любое исключение ведёт к повторной отправке без `reduceOnly`, ошибка второй попытки только логируется (`Can't delete binance order`) |
| Асинхронный вызов | `_safe_from_time_err_call_binance` вызывает синхронный клиент и `time.sleep` прямо в корутине |
