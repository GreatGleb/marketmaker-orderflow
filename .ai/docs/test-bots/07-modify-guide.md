# 07. Как вносить изменения — рецепты

Прочитать перед правкой. Каждый рецепт — точный список файлов и мест.

## Правила этой подсистемы

1. **Цикл удержания — горячий** (`demo_test_bot.py:441-498`, шаг 0.1 с,
   умножается на число активных ботов). Никаких запросов в БД, создания
   сессий, `logging.info` на каждый тик, обращений к Binance REST внутри него.
   Всё, что можно, считать до входа в цикл.
2. **Стратегии — чистые функции.** Расчёты добавляйте в
   `price_calculator.py` / `exit_strategy.py` (stateless, легко тестировать),
   а не в `demo_test_bot.py`.
3. **Конфиг бота — снимок.** Всё, что меняется по ходу работы, читайте
   через Redis (как копиботы), а не запросом к `test_bots` в цикле.
4. **`bot_config` может быть трёх разных типов**: `BotObject` (namedtuple),
   `TestBot` из БД (копибот v2), собранный вручную `TestBot`
   (`demo_test_bot.py:168`). Новое поле должно существовать во всех трёх
   путях, иначе `AttributeError`. Особенно: у namedtuple нет методов модели.
5. **Не ломайте сопоставимость статистики.** `test_orders` — накопленный
   результат экспериментов. Изменение логики выхода/входа делает старые и
   новые строки несравнимыми. Если меняете поведение — либо новое поле-флаг
   в `test_bots`, либо фиксируйте дату изменения в `toDo.yml`.

## Рецепт: добавить новый параметр бота

1. Поле в модели: `general/app/db/models.py:430` (`TestBot`).
2. Миграция: `cd general && alembic revision --autogenerate -m "..."`;
   файлы — `general/migrations/versions/`.
3. Генерация ботов: `new_bots.py` — добавить список значений и вложенный
   цикл в `create_bots` (:329).
4. Чтение в симуляторе: `demo_test_bot.py` — в нужную фазу (см.
   [03-simulation-loop.md](03-simulation-loop.md)).
5. Если параметр должен наследоваться копиботами — **два места**:
   `ProfitableBotUpdaterCommand.get_bot_config_by_params`
   (`profitable_bot_updater.py:98-123`, сериализация в JSON) **и**
   `update_config_from_referral_bot` (`demo_test_bot.py:168`, сборка `TestBot`).
   Забудете второе — параметр молча потеряется у всех копиботов.
6. Если параметр надо видеть в разрезе сделки — поле в `TestOrder` +
   `order_data` (`demo_test_bot.py:538`).

## Рецепт: добавить новую стратегию выхода

1. Метод в `ExitStrategy` (`exit_strategy.py`) по образцу
   `check_exit_conditions` — принимает `order`, цены, возвращает `bool`
   (или кортеж, если нужно вести состояние) и выставляет
   `order.stop_reason_event`.
2. Новое значение в `StopReasonEvent` (`app/enums/event_type.py`), если
   нужна новая причина.
3. Флаг в `TestBot` + ветка в `demo_test_bot.py:444-478`.
4. Уровни, если нужны, посчитать заранее в фазе 3 (`:345-408`).

## Рецепт: добавить новую стратегию входа

Править `PriceWatcher.wait_for_entry_price` (`price_provider.py:30`) —
там уже есть развилка «MA / пробой». Функция должна вернуть
`(TradeType.X.value, price)`. Она вызывается под `asyncio.wait_for`, так что
внутренние `sleep` определяют реакцию на таймаут. Таймаут задаётся в
`demo_test_bot.py:338-347`.

## Рецепт: убрать/изменить правило «30 секунд»

`demo_test_bot.py:479-491`. Правило принудительно закрывает сделку, если
через 30 секунд после открытия чистая прибыль (отсчёт от безубытка, в тиках)
меньше 10.

Оба порога зашиты в код константами. Осмысленное улучшение — вынести их в
поля `TestBot` (например `max_hold_seconds` и `min_profit_ticks_to_hold`),
чтобы они стали ещё одним измерением перебора, а не общим ограничением для
всех ботов. Порядок действий — по рецепту «добавить новый параметр бота».

Если правило убирать совсем: сделки будут висеть до срабатывания TP/SL (или
до 12 часов у MA-ботов), число сделок в час упадёт на порядки, а
`stop_reason_event = stop-long-lose` исчезнет из данных.

## Рецепт: сменить торговую пару

Пара задаётся при генерации ботов: `new_bots.py:313`. Затем:

```bash
docker exec -it orderflow_general python -m app.scripts.new_bots   # осторожно: TRUNCATE
docker exec -it orderflow_general supervisorctl restart test_bots
```

Мягкий вариант без потери истории: `UPDATE test_bots SET is_active=false`
для старой пары (или `TestBotCrud.deactivate_bot`, `test_bot.py:142`) и
`bulk_create` новых конфигов, затем перезапуск симулятора.

## Рецепт: подхватывать изменения конфигов без перезапуска

Сейчас невозможно. Минимальная реализация: в `_run_loop`
(`demo_test_bot.py:104`) перечитывать конфиг бота из БД перед каждым вызовом
`simulate_bot`. **Осторожно:** это N запросов на N ботов на каждую сделку —
при 15 000 ботов положит БД. Правильнее: отдельный воркер раз в 30 с
складывает конфиги в Redis (как `set_profitable_bot`), а симулятор читает
Redis.

## Рецепт: ускорить / масштабировать

Что упирается:

* **N корутин × 0.1 с** — цикл удержания. Профилируйте здесь.
* **`PriceProvider.get_price` делает `GET` в Redis на каждый тик каждого
  бота.** При 15 000 ботов это 150 000 GET/с. Очевидная оптимизация —
  один общий кэш цен в памяти процесса, обновляемый одной задачей
  (`MGET` пачкой или подписка), вместо `GET` из каждой корутины.
* **Открытие сессии БД внутри `simulate_bot`** для копиботов
  (`demo_test_bot.py:236`, `:235`) — на каждую сделку. Движок синглтон, но
  сессия новая. При росте числа копиботов это заметно.

## Рецепт: воспроизвести и отладить один бот

```bash
docker exec -it orderflow_general supervisorctl stop test_bots
docker exec -it orderflow_general psql ...  # оставить is_active=true только у нужного id
docker exec -it orderflow_general python -m app.scripts.start_test_bots
```

В коде уже зашита отладка для `bot_id == 1` (`demo_test_bot.py:307`, `:310`, `:337`, `:408`, `:472`) — бот с ID 1 печатает каждую фазу.
Тот же приём: временно поменять условие на нужный ID.

## Чего делать не надо

* Писать в `test_orders` напрямую из `demo_test_bot.py` — сломается батчинг
  и производительность; очередь Redis здесь принципиальна.
* Ставить `await` на что-либо сетевое (Binance REST, Telegram) внутри цикла
  удержания.
* Вызывать `TRUNCATE` в скриптах, кроме `new_bots.py` (и там — осознанно).
* Запускать второй экземпляр `start_test_bots` при работающем supervisor —
  получите двойные сделки от каждого бота.
