# 19. Бэклог рефакторинга боевого бота

Дата: 2026-10-07. Основание —
[18-live-execution-spec.md](18-live-execution-spec.md).

Цель: подготовить существующий боевой бот к работе с полноценным
Combined Stream по отдельным парам, корректной сеткой рыночного лота и
безопасным закрытием позиций. Этот план не изменяет стратегию и не
запускает новый алгоритм: он только устраняет технические ошибки,
которые были зафиксированы в спецификации.

## Состояние

- Боевой `binance_bot.py` выключен из `supervisord`.
- Требования к исправлению описаны в
  [18-live-execution-spec.md](18-live-execution-spec.md).
- В текущем коде ещё есть расхождения с Combined Stream, фильтрами
  количества и безопасным закрытием.
- Данные для офлайн-проверки загружены и сверены по SHA-256: `aggTrades`
  за июнь–сентябрь 2026 (июнь–июль — `data/binance/aggtrades` в корне
  репозитория, август–сентябрь — `BINANCE_HISTORY_DIR`). Сплошной
  OOS-тест лонга провала за 4 месяца завершён 2026-10-09 — стратегия
  закрыта, поиск альфы в потоке ордеров тоже (раздел 18
  [15-orderflow-plan.md](15-orderflow-plan.md)). Бэклог касается только
  исполнения, стратегии под него сейчас нет.

## Задачи

### 19.1. Перевод потока сделок на Combined Stream

1. Добавить единый источник событий для бинансейского бота: получить
   список символов и подписаться на `<symbol>@aggTrade` через
   `wss://fstream.binance.com/market/stream?streams=...`.
2. Разделять потоки по нескольким соединениям, как в
   `general/app/scripts/order_book_listener.py`, чтобы не зависеть от
   ограничения одного соединения на количество сообщений.
3. Добавить корректное переподключение с нарастающей паузой и osobый
   обработчик для каждого сокета.
4. Брать время события из поля `T` сделки и не считать длительность
   потока по времени получения сообщения.
5. Сохранить существующий контракт событий: в обработчике должен
   получать vorbereтый объект сделки, а не напрямую доступ к WebSocket.

### 19.2. Исправление расчёта количества

1. При старте сохранять `stepSize`, `minQty`, `MARKET_LOT_SIZE` и
   `MIN_NOTIONAL` для каждого символа из `exchangeInfo`.
2. Проверять количество по двум сеткам: `LOT_SIZE` и
   `MARKET_LOT_SIZE`; допустимое число должно соответствовать пересечению
   сеток и быть больше текущего `minQty`.
3. Округлять бюджет вниз до `stepSize` с точностью `Decimal`, без
   преобразования в `float`.
4. Отказаться от сигнала, если количество меньше `minQty`, больше
   `maxQty` или сумма `qty * price` меньше `MIN_NOTIONAL.notional`.
5. Обновлять спецификации биржи раз в сутки и повторно проверять их
   перед отправкой заказа.
6. Добавить тесты для BTC/ETH/SOL и для символов с несколькими шагами
   лота, включая случайное изменение параметров.

### 19.3. Безопасное закрытие позиций

1. Проверять режим позиций при старте и отказываться от работы в
   `dualSidePosition`, где `reduceOnly` недоступен.
2. Закрывать через `reduceOnly=true` и отдельный детерминированный
   `newClientOrderId`, привязанный к позиции.
3. Перед повтором после ошибки сети, таймаута или неизвестного статуса
   запрашивать ордер по `origClientOrderId`:
   - `FILLED` — завершить;
   - `NEW` / `PARTIALLY_FILLED` — ждать;
   - `-2013` — повторить с тем же идентификатором;
   - `-2022` — проверить позицию и статус, не повторять вслепую.
4. Удалить синхронный HTTP-вызов и `time.sleep` из корутины;
   использовать асинхронный клиент и последовательный цикл событий.
5. Сохранить `STOP_MARKET` с `closePosition=true` после входа, чтобы
   исключить оставление открытой позиции при падении процесса.
6. Добавить тесты для повторов, статусов `FILLED`, `PARTIALLY_FILLED`,
   `-2013`, `-2022` и редкого случая отсутствующей позиции.

### 19.4. Проверка безопасности и включение

1. Добавить интеграционные тесты на конфигурацию Combined Stream,
   фильтры лота и арифметику закрытия.
2. Запустить бота в бумажном режиме с проверкой реального потока,
   но без отправки реальных_ordеров.
3. Проверить отдельные соединения по парам, повторное подключение,
   количество событий и защиту от дублирования.
4. Сделать отдельный небоевой запуск после успешной проверки данных,
   а только затем включить бота в `supervisord`.

## Критерии готовности

- Все требования из [18-live-execution-spec.md](18-live-execution-spec.md)
  покрыты тестами и проверены на реальном потоке.
- Каждое открытие и закрытие проходит проверку `stepSize`,
  `MARKET_LOT_SIZE`, `MIN_NOTIONAL` и режима позиции.
- Повтор закрытия не может создать вторую встречную позицию.
- Нет синхронных вызовов и `time.sleep` внутри корутин.
- Бот проходит бумажный прогон и имеет проверенный журнал событий.
- Боевой бот включён только после подтверждения владельца.

## Данные для проверки

Это отдельный этап, не часть расчёта стратегии:

1. Скачать `aggTrades` за июнь, июль, август и сентябрь 2026 по всем
   567 парам из Binance Futures.
2. Сохранить архивы и `.CHECKSUM` в каталоге
   `data/binance/aggtrades/`.
3. Проверить SHA-256 после загрузки и повторно загрузить только файлы,
   которые не прошли проверку.
4. После целостности подтвердить итоговый объём и список неудачных
   файлов. Только после этого можно переходить к аналитике.
