# 10. Ретеншн — почему база не съедает диск

Подсистема пишет в базу непрерывно и помногу. Без чистки 80 ГБ на сервере
вроде CCX13 кончаются примерно за неделю, и кончаются они молча: сначала
тормозит Postgres, потом падает всё.

Этот документ — про то, что удаляется, когда, и почему именно так.

## Что растёт

| Таблица | Кто пишет | Сколько |
|---|---|---|
| `asset_history` | `symbols_history` (питатель цен) | 473 МБ/сутки на 50 парах |
| `test_orders` | `insert_test_orders` из очереди Redis | до 42 млн строк и 13 ГБ/сутки на полном парке |
| `asset_order_book` | сборщик стаканов | небольшая, но растёт постоянно |

## Что происходит

Два процесса по расписанию Celery (`general/app/tasks.py`):

| Задача | Как часто | Что делает |
|---|---|---|
| `app.tasks.test_order_rollup` | раз в 10 минут | сворачивает закрытые блоки `test_orders` в `test_order_rollups` |
| `app.tasks.retention` | раз в час, в :20 | удаляет старое из трёх таблиц |

Раз в час, а не раз в сутки, намеренно: суточный проход означал бы 42 млн
строк одним `DELETE`. Это одна транзакция, один снимок и кусок WAL на
несколько гигабайт — база встаёт колом, а autovacuum не может освободить
место, пока транзакция жива. Часовой проход сносит 1/24 объёма и проходит
незаметно.

## Сроки хранения

Все настраиваются через `general/.env`, умолчания — в
`general/app/config.py`.

| Таблица | Умолчание | Почему столько |
|---|---|---|
| `asset_history` | 24 ч | цены боты берут из Redis, а запросы волатильности смотрят назад максимум на сутки |
| `asset_order_book` | 24 ч | дальше суток никто не читает |
| `test_orders` | 72 ч | **48 ч — жёсткий минимум**, см. ниже. Плюс сутки запаса |
| `test_order_rollups` | **бессрочно** | последнее, что осталось от эксперимента, — удаляет человек, а не расписание |

### Почему `test_orders` нельзя держать меньше 48 часов

`new_bots.py:283` раздаёт копиботам окна прибыльности вплоть до 2880 минут.
Если сырых сделок за 48 часов в базе нет, длинное окно молча посчитается по
обрезанной истории: ни ошибки, ни записи в логе — просто рейтинг поедет, и
эксперимент будет мерить не то, что задумано.

`RETENTION_TEST_ORDERS_HOURS` меньше 48 ставить нельзя. Проверка на это есть
в `tests/test_retention_windows.py`.

## Почему сырые сделки можно удалять

Сами по себе — нельзя, это результат эксперимента. Поэтому перед удалением
каждый десятиминутный блок сворачивается в `test_order_rollups`: одна строка
на сочетание (блок, бот, пара, реферальный бот) с числом сделок, числом
прибыльных, суммарным P/L, суммарной комиссией и разбивкой по причинам
закрытия.

Десять минут выбраны не случайно: все окна прибыльности копиботов кратны
десяти (10, 20, ..., 1440, 2880), поэтому любое из них собирается из целых
блоков без потерь.

**Ретеншн никогда не опережает свёртки.** Граница удаления — это меньшее из
двух: срок хранения и конец последнего свёрнутого блока. Если свёртки встали,
чистка `test_orders` встаёт вместе с ними и в логе появляется

```
test_orders: свёртки отстают (... против ...), чистим только до границы свёрнутого
```

Это не авария, а защита: лучше занять диск, чем стереть сделки, от которых
не осталось статистики.

Что теряется при чистке: отдельные сделки — цены входа и выхода, тики, время
удержания. Что остаётся: агрегаты по каждому боту с шагом в десять минут.

Читает их `top_bots_report.py` — сразу из обоих источников: свёртки до
границы свёрнутого, сырые сделки после неё. Ветки стыкуются по watermark и
не перекрываются, поэтому сделки на стыке не считаются дважды. Копиботы в
`get_sorted_by_profit` продолжают ходить только в `test_orders`: их окна не
длиннее 48 часов, а свежесть там важнее глубины.

## Сколько это стоит на диске

Свёртки не бесплатны, и их объём **не зависит от числа сделок** — только от
числа ботов: каждый активный бот даёт строку на каждый блок.

Замерено на настоящей таблице, парк 17 236 ботов:

| | |
|---|---|
| строк свёрток за сутки | 2 481 984 |
| байт на строку (с индексами) | 269 |
| объём за сутки | 637 МБ |
| за 2 месяца | 38 ГБ |
| за полгода | 113 ГБ |
| за год | 227 ГБ |

Свёртки **не удаляются автоматически**: `RETENTION_ROLLUP_DAYS` по умолчанию
не задан, и это означает «хранить бессрочно». Ноль, пустая строка и
отрицательные значения означают то же самое — кривая настройка не должна
оборачиваться потерей единственного, что осталось от эксперимента.

Но расти они будут, и следить за этим придётся. Для парка поменьше делить
пропорционально: `637 МБ × ботов / 17236` в сутки.

Ориентир по всей базе на полном парке: 72 часа `test_orders` — около 39 ГБ,
`asset_history` — меньше гигабайта, остальное свободное место уходит под
свёртки. На диске в 80 ГБ это примерно **два месяца**, дальше нужно решение:

* **свёртки свёрток** — пересобрать старое с шагом час или сутки вместо
  десяти минут. Суточный шаг ужимает объём в 144 раза;
* **выгрузка в архив** — `COPY test_order_rollups TO ...` за нужный период,
  файл наружу, строки удалить;
* **срок хранения** — выставить `RETENTION_ROLLUP_DAYS` в сутках, и чистка
  начнёт удалять старое сама.

Сколько уже занято и за какой период:

```bash
docker exec -it orderflow_postgres psql -U postgres -c "
select pg_size_pretty(pg_total_relation_size('test_order_rollups')) as занято,
       min(bucket_start)::date as с, max(bucket_start)::date as по
from test_order_rollups;"
```

Удалить руками за период:

```sql
DELETE FROM test_order_rollups WHERE bucket_start < '2026-07-01';
```

## Почему обычного DELETE достаточно

`DELETE` не возвращает место операционной системе — он возвращает его самой
таблице. Освобождённые страницы попадают в карту свободного пространства, и
новые строки пишутся в них, а не в конец файла. Таблица перестаёт расти —
для сервера это ровно то, что нужно.

Проверено на цикле «вставить час тиков → удалить самый старый час → vacuum»,
таблица в миллион строк:

| Цикл | Строк | heap | Индексы | Всего |
|---|---|---|---|---|
| 1 | 1 000 000 | 213 МБ | 360 МБ | 573 МБ |
| 2 | 1 000 000 | 213 МБ | 372 МБ | 585 МБ |
| 3–8 | 1 000 000 | 213 МБ | 372 МБ | **585 МБ** |

Размер выходит на полку и дальше не двигается.

Обратите внимание на соотношение: индексы весят почти вдвое больше данных.
У `asset_history` их пять, самый тяжёлый — составной
`idx_assethistory_symbol_event_price` (296 МБ на миллион строк). Планируя
место, считать надо по `pg_total_relation_size`, а не по числу строк.

Шестым до миграции `d5b3e8f1a06c` лежал `ix_asset_history_id` — полный дубль
первичного ключа, приехавший из `primary_key=True, index=True` в модели.
`primary_key=True` уже создаёт уникальный btree, `index=True` добавляет
второй по той же колонке. Пользы ноль: единственное место в коде, которое
ходит по `asset_history.id` (`new_bots.py`, джойн на ранжирующий CTE),
получает ровно тот же план на `assets_history_pkey`, с той же стоимостью.
Стоил он 43 МБ на 2 млн строк — 11% индексов таблицы, плюс обновление на
каждой вставке и обход на каждом проходе autovacuum. Остальные пять нужны
все.

### Как часто убирается мусор

`DELETE` помечает строки мёртвыми, а место возвращает autovacuum. По
умолчанию он ждёт, пока мёртвыми станут 20% таблицы, — для `test_orders` это
14 часов накопления и до 7.8 ГБ мусора на диске, которого и так в обрез.
Поэтому у неё свой порог:

```sql
ALTER TABLE test_orders SET (autovacuum_vacuum_scale_factor = 0.05);
```

Ставится миграцией `c4a91e7b2d38`. Почему именно 0.05 — у прохода autovacuum
есть фиксированная цена, обход всех индексов целиком, независимо от числа
найденных мёртвых строк. Замер на 2 млн строк с тремя индексами:

| Мёртвых | Проход | Убрать 400 тыс. мёртвых |
|---|---|---|
| 0.5% | 103 мс | 40 проходов = 4120 мс |
| 2% | 124 мс | 10 проходов = 1240 мс |
| 5% | 132 мс | 4 прохода = 528 мс |
| 20% | 239 мс | 1 проход = 239 мс |

То есть чаще — почти линейно дороже суммарно. С другой стороны, всё, что
накопилось между проходами, лежит на диске:

| scale | Срабатывает | Мусора на диске |
|---|---|---|
| 0.2 (умолчание) | раз в 14.4 ч | 7.8 ГБ |
| **0.05** | **раз в 3.6 ч** | **2.0 ГБ** |
| 0.01 | раз в 0.7 ч | 0.4 ГБ |

0.05 — середина: около 6 ГБ экономии ценой четырёх проходов вместо одного.

`asset_history` намеренно оставлена с умолчанием: вся таблица меньше
гигабайта, экономить там нечего, а индексов у неё пять и проход самый
дорогой из всех.

**Порог не поможет, если в базе висит старая транзакция.** Autovacuum не
трогает строки, которые могут понадобиться хоть одному живому снапшоту, —
поэтому один воркер, забывший закрыть транзакцию, отменяет весь ретеншн:
`DELETE` проходит, а место не возвращается. Так и было у
`set_profitable_bot` до 2026-09-09 (см. [08-gotchas.md](08-gotchas.md),
пункт 19). Если таблица растёт при работающем ретеншне, смотреть здесь:

```sql
select pid, state, now() - xact_start as tx_age, query
from pg_stat_activity
where xact_start is not null and now() - xact_start > interval '5 minutes'
order by xact_start;
```

Опасаться частых проходов не нужно. Обычный `VACUUM` берёт
`ShareUpdateExclusiveLock`, который не конфликтует ни с `INSERT`, ни с
`SELECT`, и вдобавок сам себя тормозит (`autovacuum_vacuum_cost_delay`).
Замер под непрерывной вставкой: autovacuum убрал 600 000 мёртвых строк, темп
вставки не просел ни на одну запись, худшая задержка 0.76 мс против 0.2 мс
фона. Гасить ботов не нужно — в отличие от `VACUUM FULL`, который берёт
`AccessExclusiveLock` и блокирует даже чтения (532 мс на игрушечной таблице,
десятки минут на настоящей). `VACUUM FULL` в коде нет.

### Когда нужен pg_repack

Один случай: таблица разово раздулась (чистка стояла неделю) и место нужно
вернуть именно диску. Тогда `RETENTION_REPACK=true`, один проход, и обратно
в `false`.

Цена — свободное место в размер таблицы вместе с индексами: repack строит
копию рядом. **На заполненном диске он его добьёт**, а заполненный диск —
это ровно та ситуация, в которой за ним тянутся руки. По умолчанию выключен.

Отдельная тонкость: сразу после массового удаления один `VACUUM` место
индексов не отдаёт. Страницы b-tree помечаются удалёнными, но пригодными к
переиспользованию становятся только на следующем проходе — поэтому «удалил,
провакуумил, вставил заново» разово даёт рост, а установившийся режим выше
его не даёт.

## Как удаляется

`BaseCrud.delete_older_than_in_batches` — пачками по
`RETENTION_BATCH_ROWS` (50 000) с коммитом после каждой и потолком по
времени `RETENTION_MAX_SECONDS` (900 с на все три таблицы, поровну).

Не успел за проход — честно сообщает об этом и добирает через час. Данные
не застревают: следующий проход начинает с того же места.

Форма запроса важна:

```sql
DELETE FROM asset_history
WHERE ctid IN (SELECT ctid FROM asset_history WHERE event_time < :cutoff LIMIT :batch)
```

Именно `ctid IN (...)`, а не `USING`: с `USING` планировщик соединяет таблицу
с подзапросом хэшем и ради этого читает её целиком на каждой пачке. Замер на
двух миллионах строк — 5.9 с против 0.9 с, и разрыв растёт вместе с таблицей,
то есть ровно там, где чистка и нужна.

## Диагностика

```bash
# Размеры — главный индикатор
docker exec -it orderflow_postgres psql -U postgres -c "
select relname, pg_size_pretty(pg_total_relation_size(relid))
from pg_catalog.pg_statio_user_tables
order by pg_total_relation_size(relid) desc limit 5;"

# Насколько свёртки отстают от текущего момента
docker exec -it orderflow_postgres psql -U postgres -c "
select max(bucket_start), now() - max(bucket_start) as отставание
from test_order_rollups;"

# Самая старая сырая сделка — не должна уходить дальше срока хранения
docker exec -it orderflow_postgres psql -U postgres -c "
select min(created_at) from test_orders;"

# Логи задач
docker logs orderflow_celery_worker 2>&1 | grep -E "asset_history:|test_orders:|Свёрнуто"
```

Разово, руками:

```bash
docker exec -it orderflow_general python -m app.workers.test_order_rollup
docker exec -it orderflow_general python -m app.workers.retention
```

| Симптом | Причина |
|---|---|
| `test_orders` растёт, в логе «свёртки отстают» | встал `test_order_rollup`: смотреть `orderflow_celery_beat` и `orderflow_celery_worker` |
| в логе «свёрток ещё нет, сырые сделки не трогаем» | первый запуск, свёртки догоняют — нормально, если отставание сокращается |
| «хвост остался на следующий проход» каждый час | накопился большой долг либо мал `RETENTION_MAX_SECONDS` |
| размер не падает после чистки | так и задумано, см. «Почему обычного DELETE достаточно» |

## Проверки

```bash
docker exec -it orderflow_general python -m tests.test_retention_windows
```

Границы, арифметика блоков, защита от опережения свёрток — на заглушках,
идут где угодно.

```bash
docker exec -it orderflow_general python -m tests.test_report_windows
```

Деление окна отчёта между свёртками и сырьём: стык без нахлёста и щели,
выравнивание по блоку, совпадение колонок обеих веток объединения.
