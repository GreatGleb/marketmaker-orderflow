### Порядок

```bash
# 1. Новый инстанс: Ubuntu 24.04, 4 ядра / 8 ГБ / 80 ГБ, docker + плагин compose
git clone <репозиторий> /opt/marketmaker-orderflow
cd /opt/marketmaker-orderflow
tar xzf ~/orderflow-config-2026-09-23.tar.gz      # положит general/.env

# 2. Сначала ТОЛЬКО база
docker compose up -d db
docker cp ~/orderflow-2026-09-23.dump orderflow_postgres:/tmp/
docker exec orderflow_postgres pg_restore -U postgres -d postgres \
  --clean --if-exists /tmp/orderflow-2026-09-23.dump

# 3. Теперь остальное
docker compose up -d --build

# 4. Сверка
docker exec orderflow_postgres psql -U postgres -d postgres -c "
select 'rollups' t, count(*) from test_order_rollups
union all select 'bots', count(*) from test_bots
union all select 'strategy_pairs', count(*) from strategy_pairs;"
docker exec orderflow_general supervisorctl status
```

### Две ловушки

* **`boot.sh` накатывает `alembic upgrade head` при старте контейнера** и
  создаёт пустые таблицы. Поэтому база поднимается отдельным шагом и
  восстанавливается **до** того, как поднят `general`. Иначе `pg_restore`
  упрётся в уже существующие таблицы.
* **После восстановления не запускать `./run.sh init`.** Он пересоберёт
  `watched_pair` и пересоздаст парк, то есть сотрёт ровно то, ради чего
  снимался дамп. Сетки ботов детерминированы (`Random(0).shuffle` в
  сидах) и воспроизводятся, а **состав пар — нет**: скринер отбирает их по
  живому рынку за пять минут наблюдения, и второй раз получится другой
  набор. Смена пар обнуляет сопоставимость с накопленной статистикой —
  см. [../../rules/experiments.md](../../rules/experiments.md).

Если `pg_restore` ругнётся на циклические внешние ключи — добавить
`--disable-triggers`. Предупреждение самого `pg_dump` про них безвредно:
оно относится к дампам `--data-only`, а у нас полный `-Fc` со схемой.

Подробный разбор с графиками — в отчёте для трейдера (HTML, вне

Окно 2026-09-22 19:50 — 2026-09-23 14:05 UTC, 18.3 часа, 4046 ботов,
**426 370 сделок**.

* Чистый убыток парка **−428 135**, уплаченная комиссия **−426 370**.
  Валовое до комиссии — **−0.004 на сделку**, это 0.4 стандартной ошибки
  от нуля. **Сноса нет.**

  по −8.54, выход по времени 255 973 шт по −1.90. Складывается в ноль —
  так выглядит мартингейл, нарезанный целью, стопом и таймаутом.

  11 положительных. На честной единице наблюдения (час, а не сделка —
  сотни ботов торгуют одну ценовую серию, их сделки не независимы)
  максимальная положительная t по всем парам **+1.34**, значимых плюсов
  нет ни одного.
* Устойчивая тяга ≈ **−0.4 валового на сделку** против круговой комиссии
  **1.0**. Эффект меньше издержки на его извлечение, поэтому не работает
  ни одна вариация семейства: как есть −1.4, развернуть сигнал −0.6,
  развернуть и войти лимитом −0.25.
* Копиботы v3 — встроенная проверка отбора вперёд — **−8.9%** (фикс.
  баланс) и **−19.7%** (компаундинг) за 18 часов.
* `strategy_id=1` — `legacy` (пробой), `strategy_id=3` — `strategy_1`
  (возврат к средней). Валовое: **+0.03** против **−1.57**. Возврат вдвое
  хуже, получая скидку на комиссии за лимитный вход. Его убыток — самый
  воспроизводимый эффект во всей выборке.

**Вывод, определяющий план:** перебирать сетку выхода бессмысленно,
вопрос сместился на **признак входа**.

### 6. Тормоз по BTC

**Проверен на собранных сделках 2026-09-23, разработку не начинаем**
(числа и границы вывода — раздел 7.3). Дальше — как его пришлось бы делать, если гипотеза
когда-нибудь воскреснет на данных обвала.

Подключается **в одном месте**: обёртка `before_entry` в
`general/app/bots/demo_test_bot.py`, через которую все три стратегии
обязаны пропускать любое ожидание до входа (`context.before_entry` в
каждой из трёх `algorithm.py`). Внутри уже сидит проверка копибота «не
отозван ли донор», механика отработана. Сам тормоз — ключ в Redis с TTL
600 секунд по образцу `most_volatile_symbol_*` плюс проверка в обёртке.
Стратегии не трогаются.

Два нюанса:

* **BTC в данных нет.** `watched_pair` собирается скринером по
  волатильности и скачкам, BTC такой отбор не проходит. Нужен отдельный
  питатель; дешевле всего поллинг `/fapi/v1/klines`, он уже реализован в
  `general/app/scripts/watch_binance_candles.py` в режиме `rest`.
* «Снимать расставленные сетки» — это не только блокировка входа. У
  стратегии B висит лимитная заявка с дедлайном `max_wait_seconds`, и
  тормоз должен рвать это ожидание. Два места, а не одно.

### 7. Проактивная сетка = стратегия B

Всё описанное в задании уже работает в `strategy_1`:

| Из задания | В коде |
|---|---|
| Лимитка на K × ATR | `entry_offset_atr` — 1.5 / 2.5 / 3.5 |
| Пересчёт цены, подтяг за рынком | «Уровни пересчитываются на ходу: пока заявка висит, ATR меняется» |
| Post-Only, комиссия maker | `entry_is_maker` |
| Ожидание исполнения | `max_wait_seconds` — 300 с |

И результат известен: **−1.57 валового на сделку**, худший в парке.

Новое в задании ровно одно: B торгует **откат** (цель задана как доля
пройденного отступа), а замысел задания — ехать **вместе с движением**.
Такого режима в сетке B нет. Делать не переписыванием прострелов, а
**новым измерением `exit_mode` (откат / продолжение) в сетке B**: вся
машинерия лимитного входа переиспользуется, сетка растёт с 243
конфигураций до 486, результат сразу сравним с уже собранными числами.

## 4. Достоверность симулятора

Самостоятельный блок работ, который всплыл при разборе задания 7. Это
**рефакторинг модели исполнения**, а не новая функциональность.

### Спред не моделируется вообще — и это крупнее post-only

Поток `bookTicker` приносит лучшие bid и ask, но в
`general/app/scripts/watch_ws_and_save.py` они схлопываются в середину
(фрагмент `item["c"] = str((Decimal(bid) + Decimal(ask)) / 2)`), и
записывается только она. Сами bid и ask выбрасываются, в `AssetHistory`
их колонок нет.

То есть **все наши числа посчитаны так, будто покупка и продажа
происходят ровно посередине спреда**. В реальности рыночный вход идёт по
ask, выход по bid — целый спред за круг сверх комиссии.

**Замерено 2026-09-23** (раздел 7): поправка **0.264 на сделку** против
комиссии 0.992, то есть издержки больше на четверть, а валовое парка
уезжает с −0.061 до **−0.325**.

Колонки заведены: `best_bid_price`, `best_bid_qty`, `best_ask_price`,
`best_ask_qty` в `AssetHistory`, разбор — `book_top` в
`general/app/scripts/watch_ws_and_save.py`. Заполняются только там, где
источник их отдаёт: спотовый `bookTicker` и спотовый `@ticker`. У
фьючерсного `!ticker@arr` и у REST `/fapi/v1/ticker/24hr` полей bid/ask
нет вовсе, а `MARKET_DATA_SOURCE` сейчас `ws` — значит при нынешней
настройке колонки останутся пустыми. Чем заполнить на фьючерсах, с
дешёвого пути — в 7.4.

Это же меняет знак в задании 7: у лимитного входа спред не платится, а
**зарабатывается**. Без модели спреда сравнение maker и taker
некорректно, и строка «обе ноги лимитом = 0.0» из отчёта занижена.

### Остальные слои

| Что | Решаемо | Чем |
|---|---|---|
| Отказ post-only | Да, но не на любом фиде | Как только есть best bid/ask: заявка, оказавшаяся пересекающей при подтяге, отклоняется. Цена и края книги обязаны быть из одного сообщения — иначе ответ неверен, см. 7.4 |
| Исполнилась ли заявка (очередь) | Приближённо | Объём впереди — видимый размер уровня при выставлении, съедается объёмом сделок по этой цене. Нужны задания 1 и 2 |
| Разрыв книги на шпиле | Да | `aggTrade` даёт реальные цены сделок: «торговалось ли по нашему уровню» отвечается прямо |
| Задержка решение → ордер | Да, дёшево | Исполнять по цене через N мс. Важнее всего для реактивных прострелов |

**Не решается:** настоящая позиция в очереди (своего места не видим,
отмены впереди делают оценку пессимистичной, айсберги оптимистичной),
собственное влияние на рынок (при номинале 1000 пренебрежимо), точная
семантика матчинга.

### Как вводить

Любая из поправок меняет все числа разом и снова обнуляет сопоставимость.
Поэтому вводить **теневым замером**: для каждой симулированной сделки
дополнительно записывать, исполнилась бы она по реалистичной модели и по
какой цене, не трогая сам поток сделок. Тогда размер поправки будет
измерен, а не назначен, — и станет известно, насколько −428 тысяч
оптимистичны, прежде чем менять правила игры.

Отдельно помнить: `profit_loss` в `test_orders` **уже чистый**,
`calculate_pnl` в
`general/app/sub_services/logic/price_calculator.py` вычитает обе ноги.
Валовое считается как `profit_loss + open_fee + close_fee`.

## 5. Порядок работ и почему такой

1. **Восстановить сервер** (раздел 1) и дать парку работать. Вывод
   «нулевой снос» доказан для одного режима рынка; неделя даст выходные,
   азиатскую сессию и хотя бы один обвал.
2. **Завести парк прострелов.** Готов, стоит одной команды, ни от чего не
   зависит, даёт третью стратегию в наблюдении сразу.
3. ~~**Проверить тормоз по BTC на уже собранных сделках.**~~ **Сделано
   2026-09-23** — раздел 7.3. Эффекта нет в том диапазоне движений,
   который случился; разработку не начинаем, переспросить на данных
   обвала.
4. ~~**Померить спред** по REST (раздел 4).~~ **Сделано 2026-09-23**:
   поправка 0.264 на сделку, +27% к издержкам — раздел 7.
5. **Поток и метрики.** `aggTrade` → дельта (окна 1/5/15/60 с, CVD,
   Relative Delta) → Redis; `@depth20@100ms` → OBI и детектор стен →
   Redis. Оба провайдера добавляются в `MarketContext`
   (`general/app/strategies/base.py`) рядом с `price_provider` и
   `candle_provider` — ядро симулятора не меняется, вся логика остаётся в
   стратегиях.
6. **Запись признаков без гейта.** Дельта и OBI пишутся в момент входа,
   решение о входе не меняется.
7. **Гейты и тормоз** — с порогами, выбранными из данных шагов 3, 4 и 6.
8. **`exit_mode` продолжения** в сетке B (задание 7).

### Почему запись раньше гейта

Постановка задания 3 требует сразу гейтить вход по порогам, взятым с
потолка (Relative Delta > 60%, «OBI сдвинут в сторону движения», K сигм).
Мы установили, что сноса во входе нет. Если навесить фильтр с угаданным
порогом и перезапустить парк, через неделю получится **один бит** — стало
лучше или хуже, — на выборке, несопоставимой со старой, и без ответа,
порог виноват или сам признак.

Запись без гейта даёт на тех же сделках условное распределение валового
P/L по каждому признаку, и порог выбирается из данных. Разработка метрик
при этом одинакова в обоих вариантах, так что ничего не откладывается:
меняется только то, что происходит на шаге 7.

## 6. Что нельзя забыть

* **Зафиксировать даты.** Заведение `strategy_0`, ввод поправок на спред,
  любой гейт входа — каждое обнуляет сопоставимость с накопленным. Правило
  и причины — [../../rules/experiments.md](../../rules/experiments.md).
* **Ссылки на код — якорем, а не номером строки**
  ([../../rules/docs-references.md](../../rules/docs-references.md)).
* **`top_bots_report` не читать как список находок.** При 4046 участниках
  максимум по чистой случайности ожидается около +300 за сутки, а лучший
  бот дал +348.
* **Единица наблюдения — час, а не сделка.** t по сделкам завышена в разы:
  сотни ботов торгуют одну ценовую серию.
* **Фид чистый** — проверено: диапазоны цен узкие, максимальное движение
  внутри сделки 7–12%, нормально для низколиквидных альтов. Убыток
  настоящий, не артефакт данных.

### 7.2. Спред: поправка 0.264 на сделку

| валовое на сделку, парк | −0.061 | 0.264 | **−0.325** |
| валовое, `legacy` | +0.015 | 0.269 | −0.254 |
| валовое, `strategy_1` | −3.020 | — | −3.020 |

**`strategy_1` поправки не получает — она уже платит своё.** Это

счёт. На парк это влияет на 0.7% поправки, заголовок 0.264 держится.

одной стратегии начислено проскальзывание, другой ноль. Разрыв между ними
меньше, чем выглядит.

Снизу: на всех 55 парах лучший уровень держит меньше $1000 в медианном

утверждение про типичное состояние книги, а не про каждый тик. Сверху:
модель считает **все** выходы рыночными, а 29.3% сделок (146 552) закрылись
по тейку, который на бирже вполне может стоять лимиткой. Если считать тейк
maker-ногой, поправка падает до **0.221** (+22% вместо +27%).

### 7.3. Тормоз по BTC: эффекта нет там, где было что мерить

Минутные свечи BTCUSDT из `/fapi/v1/klines` за 22–23 сентября (2532
штуки), join по минуте открытия сделки.

**Порога из постановки не было ни разу на пятиминутном окне.** Максимум
`|ΔBTC_5m|` за все 2532 минуты — **0.894%**; минут выше 1.5% ноль, выше
1.0% тоже ноль. На пятнадцатиминутном окне случаи есть: максимум
**1.63%**, выше 1.5% четыре минуты, выше 1% — четырнадцать. То есть
«за считанные минуты» порог достижим, если мерить не пятиминуткой.

Валовое, очищенное от средних по «пара × стратегия», единица наблюдения —
минута (по правилу раздела 6, а не по сделке). Минуты **не взвешены** по
числу сделок: минута с одной сделкой весит столько же, сколько минута с
пятьюстами, поэтому t в таблице читаются как ориентир, а общее среднее по
минутам −0.066, а не ноль:

| \|ΔBTC_5m\| | минут | сделок | остаток | t |
|---|---|---|---|---|
| < 0.10 | 964 | 364 915 | −0.044 | −0.85 |
| 0.10–0.20 | 236 | 84 281 | −0.092 | −0.86 |
| 0.20–0.30 | 67 | 25 153 | −0.471 | −2.14 |
| 0.30–0.50 | 25 | 12 084 | −0.218 | −0.59 |
| > 0.50 | 12 | 13 544 | **+1.286** | +1.17 |

Зависимость немонотонна, самый бурный бакет — плюс, единственный t за −2
живёт на 67 минутах из 1304 и не переживает поправку на пять сравнений.
Корреляция остатка с `|ΔBTC_5m|` **+0.019**, с `|ΔBTC_1m|` **+0.052**, с
`|ΔBTC_15m|` **−0.021** — все три около нуля, у двух знак противоположен
гипотезе. Знаковая проверка тоже пустая: BUY хуже всего в спокойные
минуты (−0.199), SELL при падении BTC круче −0.3% даёт **+0.760**, лучшая
из десяти ячеек.

### Движение вперёд: то, ради чего тормоз и задумывался

Всё выше смотрит **назад** от момента входа, а содержательная постановка
тормоза — про движение **вперёд**: плохо ли входить прямо перед тем, как
BTC поедет. Проверено отдельно.

Модульная форма (собственно волатильность) пуста и вперёд: корреляция
остатка с `|Δ вперёд 5м|` **+0.031**, бакеты той же немонотонной кашей,
на 3/10/30 минутах ничего.

Знаковая форма вперёд даёт на минуте слабый след одного знака на всех
горизонтах 3–15 минут: `f3` **−0.058** (t −2.08), `f5` −0.050, `f15`
−0.051; со взвешиванием по числу сделок до −0.087 (t −3.14). Читается это
как «BTC растёт в ближайшие минуты → парку хуже».

**Но он не переживает честную единицу наблюдения.** На неперекрывающихся
блоках: 15 минут t −1.42, 30 минут t −0.26, **час — t +1.15 по `f3` и
+1.11 по `f5`, то есть знак переворачивается**. Прореживание по фазе даёт
по `f15` разброс от +0.195 до −0.539: эффект сидит в горстке минут. По
парам — орёл-решка: знак отрицателен у 29 пар из 52, положителен у 23.
Размер и без того не окупает разговора: наклон −1.0 валового на 1%
движения BTC, при sd = 0.124% это −0.12 на сделку на сигму против
комиссии 0.99.

### Чего эта проверка НЕ доказала

Отрицательный ответ здесь узкий, и путать его с «BTC не влияет» нельзя.
Мощность по бакетам (минимально различимый эффект, 80% при α = 0.05):

| \|ΔBTC_5m\| | минут | различимый эффект |
|---|---|---|
| < 0.10 | 964 | **0.15** |
| 0.10–0.20 | 236 | 0.30 |
| 0.20–0.30 | 67 | 0.62 |
| 0.30–0.50 | 25 | 1.04 |
| > 0.50 | 12 | **3.08** |

То есть в спокойных минутах видно эффект вшестеро меньше комиссии — и его
там нет. **А в самом бурном бакете видно только эффект от 3.08 на сделку,
втрое больше комиссии.** Тормоз, который спасал бы 0.5–1.0 на сделку в
бурные минуты, эта проверка **не увидела бы**. Двенадцать минут — не
выборка. По корреляции то же самое: на минуте различимо r от 0.078
(наблюдали +0.019), на часе — только от **0.61**.

**Что отсюда следует.** Строить тормоз сейчас не на чем: там, где данных
много, эффекта нет, а там, где он мог бы быть, данных нет. Это основание
**не начинать разработку**, а не вывод «BTC никогда не важен». Обвала в
окне не было — максимум движения 0.894% за пять минут, — и именно на
обвале тормоз и должен был бы работать.

**Когда переспросить:** после прогона, в котором есть хотя бы один день с
движением BTC на 2–3%. Проверка стоит полчаса и повторяется тем же
способом — скачать `/fapi/v1/klines`, сджойнить по минуте, посчитать
остаток от средних по «пара × стратегия». Порог для решения задать
заранее: эффект в бурных минутах хуже спокойных на величину, сравнимую с
комиссией.

### 7.4. Bid и ask сохраняются

Колонки `best_bid_price`, `best_bid_qty`, `best_ask_price`,
`best_ask_qty` в `AssetHistory`, миграция `c7d4a29f8b15`. Разбор — функция
`book_top` в `general/app/scripts/watch_ws_and_save.py`, она же отдаёт
`BOOK_FIELDS`. Середина спреда как `last_price` не изменилась: правило
входа и выхода не тронуто, сопоставимость цела.

Три вещи, которые неочевидны:

* **набор ключей у записи всегда один и тот же**, даже когда книги нет.
  `AssetHistoryCrud.bulk_create` вставляет пачку одним многострочным
  INSERT, а колонки берутся из первой строки, и разнородная пачка
  ломается двумя разными способами: строка без ключей **первой** —
  вставка проходит, края спреда у остальных молча уходят в NULL; строка
  без ключей **после** строки с ключами — `CompileError`, который
  `save_filtered_assets` ловит своим `except Exception` и откатывает,
  теряя всю пачку котировок. Оба воспроизведены в тесте;
* **перевёрнутую или нулевую книгу отбрасываем целиком**, обе стороны. По
  половине книги считается отрицательный спред, и заметить это потом
  нечем;
* **bid и ask попали и в снимок Redis** (`price_snapshot:*`), рядом с
  ценой. Симулятор читает цену оттуда, а не из БД, так что проверке
  post-only и теневому замеру исполнения нужен именно снимок. Читатели
  разбирают его через `parse_snapshot`, лишние ключи игнорируются.
  **Но пользоваться снимком для post-only можно не в любом режиме:** при
  `MARKET_DATA_SPOT_STREAM=aggTrade` цена берётся из сделки, а bid и ask
  достаются из `@ticker` возрастом до секунды — цена может оказаться вне
  `[bid, ask]`, и проверка ответит неверно. Годится только режим
  `bookTicker`, где всё из одного сообщения.

**Где эти поля берутся.** У фьючерсного `!ticker@arr` (режим `ws`) и у
REST `/fapi/v1/ticker/24hr` полей bid/ask нет вовсе — проверено
подключением, не по памяти. Поэтому заведён отдельный режим
`futures_ws`, см. 7.6; на нём колонки и наполняются. В спотовом режиме
поля тоже приходят — из `bookTicker` и `@ticker`.

Проверка: `python -m tests.test_book_top` — разбор книги, битые и
перевёрнутые варианты, однородность набора ключей, наличие колонок в
модели. Только заглушки.

### 7.5. Сетка прострелов расширена

`WINDOW_SECONDS` получил 1 секунду, `MOVE_PERCENTS` — 2.0%
(`general/app/constants/strategy_0_seed.py`). Было 648 конфигураций,

Заводить парк по-прежнему нельзя без сервера, и мешает не только он: под

**Односекундное окно упирается в разрешение фида, и это надо решить до

односекундное окно меряет «дельту между двумя соседними тиками», а не

24-часового тикера, внутрисекундный прострел в неё не попадает в

### 7.6. Поток котировок переведён на фьючерсный `@bookTicker`

Режим `MARKET_DATA_SOURCE=futures_ws`, функция
`run_futures_ws_listener` в `general/app/scripts/watch_ws_and_save.py`.
Включён в `general/.env`.

**Зачем.** Прежний `!ticker@arr` отдаёт снимок 24-часового тикера
примерно раз в секунду и **не содержит bid/ask вовсе**. На нём нельзя ни
померить спред по факту, ни проверить post-only, ни разглядеть прострел
короче секунды — то есть три задачи сразу упирались в источник, а не в
логику.

**Два соединения, а не одно.** Фьючерсные потоки разнесены Binance по
базовым URL: `@bookTicker` живёт на `/public`, `@ticker` — на `/market`.
Замер 2026-09-23: при смешанной подписке на `/public` приходят **только**
`bookTicker`, а `@ticker` молча проглатывается. Это ровно тот отказ, что
описан в пункте 29 [08-gotchas.md](08-gotchas.md) — подписка принята,
данных нет. Поэтому два сокета со своим переподключением у каждого:
падение одного не роняет второй.

**Redis и база живут на разных частотах — это главное решение.**

| | частота | почему так |
|---|---|---|
| приходит с биржи | **834 тика/с** на 55 парах | замер 2026-09-23, медиана 3.2 тика/с на пару, максимум 256 (PTBUSDT) |
| публикация в Redis | раз в **0.05 с** на пару | столько же, сколько `PriceCache.REFRESH_INTERVAL_SECONDS`; чаще бессмысленно — в ключе живёт одно значение, монотонность отбросит промежуточные |
| запись в `asset_history` | раз в **1 с** на пару | запись каждого тика — 72 млн строк в сутки, чего не выдержит ни диск, ни ретеншн |

Секундная плотность истории выбрана не наугад: ровно столько давал
`!ticker@arr`, поэтому ни статистика волатильности (`MIN_TICKS_IN_WINDOW`
и соседние в `general/app/constants/volatility.py`), ни диск подмены не
замечают. Новое в строке — только bid, ask и их объёмы.

**`last_price` остался серединой спреда.** Края кладутся рядом, а не
вместо: по середине посчитаны все накопленные сделки, и подмена обнулила
бы сопоставимость. Логика входа и выхода не тронута.

**Как разделились обязанности.** `save_filtered_assets` получила
параметр `publish`. Фьючерсный слушатель публикует сам, раз в 50 мс, а
историю пишет раз в секунду с `publish=False`: повторная публикация того
же события вернула бы «не принято» (срок и монотонность считаются по
времени события), и записи молча отфильтровались бы — история осталась
бы пустой. Правило «в историю идут только принятые события» (пункт 25
[08-gotchas.md](08-gotchas.md)) при этом соблюдено: слушатель сам
отбирает по флагам от `publish_prices`.

**Проверено вживую** на 55 watched-парах: 38 строк в секунду, у всех
