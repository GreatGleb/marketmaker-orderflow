### Порядок

```bash
# 1. Новый инстанс: Ubuntu 24.04, 4 ядра / 8 ГБ / 80 ГБ, docker + плагин compose
git clone <репозиторий> /opt/marketmaker-orderflow
cd /opt/marketmaker-orderflow
tar xzf ~/orderflow-config-2026-09-23.tar.gz      # положит general/.env

# 2. Сначала ТОЛЬКО база
docker compose up -d db
docker cp ~/orderflow-2026-09-23.dump orderflow_postgres:/tmp/
docker exec orderflow_postgres pg_restore -U postgres -d postgres \
  --clean --if-exists /tmp/orderflow-2026-09-23.dump

# 3. Теперь остальное
docker compose up -d --build

# 4. Сверка
docker exec orderflow_postgres psql -U postgres -d postgres -c "
select 'rollups' t, count(*) from test_order_rollups
union all select 'bots', count(*) from test_bots
union all select 'strategy_pairs', count(*) from strategy_pairs;"
docker exec orderflow_general supervisorctl status
```

### Две ловушки

* **`boot.sh` накатывает `alembic upgrade head` при старте контейнера** и
  создаёт пустые таблицы. Поэтому база поднимается отдельным шагом и
  восстанавливается **до** того, как поднят `general`. Иначе `pg_restore`
  упрётся в уже существующие таблицы.
* **После восстановления не запускать `./run.sh init`.** Он пересоберёт
  `watched_pair` и пересоздаст парк, то есть сотрёт ровно то, ради чего
  снимался дамп. Сетки ботов детерминированы (`Random(0).shuffle` в
  сидах) и воспроизводятся, а **состав пар — нет**: скринер отбирает их по
  живому рынку за пять минут наблюдения, и второй раз получится другой
  набор. Смена пар обнуляет сопоставимость с накопленной статистикой —
  см. [../../rules/experiments.md](../../rules/experiments.md).

Если `pg_restore` ругнётся на циклические внешние ключи — добавить
`--disable-triggers`. Предупреждение самого `pg_dump` про них безвредно:
оно относится к дампам `--data-only`, а у нас полный `-Fc` со схемой.

### 6. Тормоз по BTC

**Проверен на собранных сделках 2026-09-23, разработку не начинаем**
(числа и границы вывода — раздел 7.3). Дальше — как его пришлось бы делать, если гипотеза
когда-нибудь воскреснет на данных обвала.

Подключается **в одном месте**: обёртка `before_entry` в
`general/app/bots/demo_test_bot.py`, через которую все три стратегии
обязаны пропускать любое ожидание до входа (`context.before_entry` в
каждой из трёх `algorithm.py`). Внутри уже сидит проверка копибота «не
отозван ли донор», механика отработана. Сам тормоз — ключ в Redis с TTL
600 секунд по образцу `most_volatile_symbol_*` плюс проверка в обёртке.
Стратегии не трогаются.

Два нюанса:

* **BTC в данных нет.** `watched_pair` собирается скринером по
  волатильности и скачкам, BTC такой отбор не проходит. Нужен отдельный
  питатель; дешевле всего поллинг `/fapi/v1/klines`, он уже реализован в
  `general/app/scripts/watch_binance_candles.py` в режиме `rest`.
* «Снимать расставленные сетки» — это не только блокировка входа. У
  стратегии B висит лимитная заявка с дедлайном `max_wait_seconds`, и
  тормоз должен рвать это ожидание. Два места, а не одно.

### 7. Проактивная сетка = стратегия B

Всё описанное в задании уже работает в `strategy_1`:

| Из задания | В коде |
|---|---|
| Лимитка на K × ATR | `entry_offset_atr` — 1.5 / 2.5 / 3.5 |
| Пересчёт цены, подтяг за рынком | «Уровни пересчитываются на ходу: пока заявка висит, ATR меняется» |
| Post-Only, комиссия maker | `entry_is_maker` |
| Ожидание исполнения | `max_wait_seconds` — 300 с |

И результат известен: **−1.57 валового на сделку**, худший в парке.

Новое в задании ровно одно: B торгует **откат** (цель задана как доля
пройденного отступа), а замысел задания — ехать **вместе с движением**.
Такого режима в сетке B нет. Делать не переписыванием прострелов, а
**новым измерением `exit_mode` (откат / продолжение) в сетке B**: вся
машинерия лимитного входа переиспользуется, сетка растёт с 243
конфигураций до 486, результат сразу сравним с уже собранными числами.

## 4. Достоверность симулятора

Самостоятельный блок работ, который всплыл при разборе задания 7. Это
**рефакторинг модели исполнения**, а не новая функциональность.

### Спред не моделируется вообще — и это крупнее post-only

Поток `bookTicker` приносит лучшие bid и ask, но в
`general/app/scripts/watch_ws_and_save.py` они схлопываются в середину
(фрагмент `item["c"] = str((Decimal(bid) + Decimal(ask)) / 2)`), и
записывается только она. Сами bid и ask выбрасываются, в `AssetHistory`
их колонок нет.

То есть **все наши числа посчитаны так, будто покупка и продажа
происходят ровно посередине спреда**. В реальности рыночный вход идёт по
ask, выход по bid — целый спред за круг сверх комиссии.

**Замерено 2026-09-23** (раздел 7): поправка **0.264 на сделку** против
комиссии 0.992, то есть издержки больше на четверть, а валовое парка
уезжает с −0.061 до **−0.325**.

Колонки заведены: `best_bid_price`, `best_bid_qty`, `best_ask_price`,
`best_ask_qty` в `AssetHistory`, разбор — `book_top` в
`general/app/scripts/watch_ws_and_save.py`. Заполняются только там, где
источник их отдаёт: спотовый `bookTicker` и спотовый `@ticker`. У
фьючерсного `!ticker@arr` и у REST `/fapi/v1/ticker/24hr` полей bid/ask
нет вовсе, а `MARKET_DATA_SOURCE` сейчас `ws` — значит при нынешней
настройке колонки останутся пустыми. Чем заполнить на фьючерсах, с
дешёвого пути — в 7.4.

Это же меняет знак в задании 7: у лимитного входа спред не платится, а
**зарабатывается**. Без модели спреда сравнение maker и taker
некорректно, и строка «обе ноги лимитом = 0.0» из отчёта занижена.

### Остальные слои

| Что | Решаемо | Чем |
|---|---|---|
| Отказ post-only | Да, но не на любом фиде | Как только есть best bid/ask: заявка, оказавшаяся пересекающей при подтяге, отклоняется. Цена и края книги обязаны быть из одного сообщения — иначе ответ неверен, см. 7.4 |
| Исполнилась ли заявка (очередь) | Приближённо | Объём впереди — видимый размер уровня при выставлении, съедается объёмом сделок по этой цене. Нужны задания 1 и 2 |
| Разрыв книги на шпиле | Да | `aggTrade` даёт реальные цены сделок: «торговалось ли по нашему уровню» отвечается прямо |
| Задержка решение → ордер | Да, дёшево | Исполнять по цене через N мс. Важнее всего для реактивных прострелов |

**Не решается:** настоящая позиция в очереди (своего места не видим,
отмены впереди делают оценку пессимистичной, айсберги оптимистичной),
собственное влияние на рынок (при номинале 1000 пренебрежимо), точная
семантика матчинга.

### Как вводить

Любая из поправок меняет все числа разом и снова обнуляет сопоставимость.
Поэтому вводить **теневым замером**: для каждой симулированной сделки
дополнительно записывать, исполнилась бы она по реалистичной модели и по
какой цене, не трогая сам поток сделок. Тогда размер поправки будет
измерен, а не назначен, — и станет известно, насколько −428 тысяч
оптимистичны, прежде чем менять правила игры.

Отдельно помнить: `profit_loss` в `test_orders` **уже чистый**,
`calculate_pnl` в
`general/app/sub_services/logic/price_calculator.py` вычитает обе ноги.
Валовое считается как `profit_loss + open_fee + close_fee`.

Зафиксировано 2026-09-23. Тиковая история нужна **не** для того, чтобы
прогонять по ней стратегию с моделью матчинга и очереди — такой бэктестер
стоит месяцев и врёт ровно в том месте, где интересно. Она нужна, чтобы
посчитать распределения и достать готовые числа: порог импульса, время
удержания, пороги по дельте. Числа уезжают в конфиг ботов-симуляторов, и
проверяет их уже симулятор на живых ценах — там, где модель исполнения
общая со всем остальным парком и сравнение честное.

Отсюда второе следствие: **сетка не растёт, а сжимается.** У `strategy_0`
сейчас 1080 конфигураций — это перебор вслепую. Он стоит месяца
наблюдения и всё равно кончается тем, что лучший бот объясняется
случайностью (раздел 6, про `top_bots_report`). После офлайн-счёта сетка
сводится к окрестности вычисленных значений — два-три соседних порога,
два-три таймаута, десятки конфигураций вместо тысячи. Нынешний парк
прострелов заводится на старой сетке только потому, что он готов и ждёт
не данных, а сервера.

Офлайн-счёт **сервера не требует** — это ноутбучная работа на скачанных
архивах, и она может идти параллельно со всем остальным списком.

### 5.1. Статистический вычет параметров (Python + data.binance.vision)

Что реально лежит в открытых дампах по USDⓈ-M фьючерсам
(`data/futures/um/daily/...`, проверено 2026-09-23 запросами к бакету):

| Набор | За прошлый месяц | Что даёт |
|---|---|---|
| `aggTrades` | есть | цена и объём каждой сделки, флаг `isBuyerMaker` → дельта и CVD в любом окне; сам импульс; секундная сетка |
| `klines/1m` | есть | ATR для нормировки импульса |
| `metrics` | есть, шаг 5 минут | открытый интерес, `takerBuySellVolume` — фон, не триггер |
| `bookDepth` | есть, но снимок раз в 30 секунд по процентным уровням ±0.2/1/2/3/4/5% | грубая плотность на минутном масштабе. Не OBI и не топ книги |
| `bookTicker` | **нет.** Публикация прекращена, последний день — 2024-03-30 | — |
| `klines/1s` | **нет** на фьючерсах, минимум 1m (1-секундные есть только на споте) | секунды собирать из `aggTrades` — это и точнее |

Что считаем. Для каждого срабатывания триггера — движение ΔP за окно W,
нормированное на ATR, при объёме V и дельте D — условное распределение
приращения цены на горизонте H. Отсчёт ведётся **не от цены в момент
триггера, а от цены через +100…200 мс**: столько занимает путь от решения
до заявки, и на прострелах это и есть разница между прибылью и тем, что
уже разобрали без нас.

Порог годится, если распределение перекрывает издержки круга. Издержки
считать по нашим, а не по спотовым ставкам:

* комиссия — **0.05% на ногу**, `COMMISSION_OPEN` и `COMMISSION_CLOSE` в
  `general/app/constants/commissions.py`. За круг это **0.1%, а не 0.2%**:
  0.1% тейкером — спотовая ставка, на USDⓈ-M тейкер вдвое дешевле;
* спред — **0.0264% за круг**, замерено на своём парке (раздел 7.2: 0.264
  на номинал 1000).

Барьер выходит **≈0.13% за круг** вместо ≈0.23%, которые получатся, если
взять спотовую ставку. Это меняет вид сетки: движение 0.3% перекрывает
издержки вдвое с лишним, а не еле-еле, и нижние пороги — рабочие, их надо
считать, а не отбрасывать заранее.

Смотреть медиану и квантили, а не среднее: у прострелов хвост в одну
сторону, и среднее покажет прибыль там, где восемь сделок из десяти
убыточные.

Результат — таблица «символ → порог импульса в %, окно, N секунд
удержания, порог дельты». Её строки едут в `strategy_0_bot_rows`
(`general/app/constants/strategy_0_seed.py`). Никакого нового рантайма
офлайн-часть за собой не тянет: это скрипт в `general/app/scripts/`,
запускаемый руками.

### 5.2. Чего офлайн получить нельзя

Три вещи, которые придётся брать из своего потока, — и поэтому шаги с
потоком из списка работ не выкидываются:

* **OBI и стены.** Публичных данных о топе книги на масштабе секунд нет
  вовсе: `bookTicker` прекращён в марте 2024, а `bookDepth` — раз в 30
  секунд, и ближайший его уровень ±0.2% на BTC отстоит от цены на
  несколько сотен долларов, весь спред и вся интересная плотность внутри
  этого зазора. Пороги по OBI можно взять только со своего
  `@depth20@100ms` — его и поднимаем локально (5.3);
* **Спред на фьючерсах** — тот же прекращённый `bookTicker`. Единственный
  источник — собственный `asset_history`, куда `best_bid_price` и
  `best_ask_price` пишутся с 2026-09-23 (раздел 7.4), и пишутся теперь
  локально (5.3);
* **Поведение наших пар.** `watched_pair` — низколиквидные альты, у части
  из них фьючерсов на Binance нет вовсе. Перед выгрузкой сверить список
  пар с каталогом дампов и честно записать, кто выпал: иначе пороги
  окажутся посчитаны по BTC и ETH и перенесены на бумаги, которые ведут
  себя иначе.

### 5.3. Сбор спреда и стакана поднимается локально

Решение 2026-09-24: воркер, который слушает `@depth20@100ms`, и питатель,
который пишет края книги в `asset_history`, работают **на ноутбуке**, а не
на арендованном инстансе. Причина — деньги: парк всё равно не крутится,
платить за сервер ради записи потока незачем, а данные нужны уже сейчас,
чтобы офлайн-счёту (5.1) было чем поверяться по нашим парам.

Половина этого уже работает: `MARKET_DATA_SOURCE=futures_ws` и
`run_futures_ws_listener` в `general/app/scripts/watch_ws_and_save.py`
пишут `best_bid_price` и `best_ask_price` раз в секунду на пару, проверено
на 55 парах (раздел 7.6). Новое — только слушатель стакана.

Что нельзя упустить при локальном сборе:

* **Ретеншн сотрёт ровно то, ради чего всё поднято.**
  `RETENTION_ASSET_HISTORY_HOURS` и `RETENTION_ORDER_BOOK_HOURS` — по 24
  часа (`general/app/config.py`), чистку гоняет celery-beat. Локально
  история копится неделями, поэтому либо сроки в `general/.env`
  поднимаются осознанно и за диском следят, либо воркер, кроме публикации
  в Redis, складывает суточные файлы на диск. Второе надёжнее: на сервере
  `asset_history` вместе со стаканом занимала 542 МБ из 720 при сроке в
  сутки, и месяц такого в Postgres на ноутбуке хранить незачем.
* **Стакан не писать в Postgres построчно.** Старый
  `general/app/scripts/order_book_listener.py` коммитил каждое сообщение;
  на 55 парах `@depth20@100ms` это ~550 сообщений в секунду с двумя
  JSON-массивами в каждом. В рантайм — Redis, в архив — файлы.
* **Локальный стек поднимается не так, как серверный.** Два `.env`
  (`general/.env` плюс корневой, для подстановки в `docker-compose.yml`),
  Redis на 6380 из-за занятого 6379, сервис `web` не поднимать, `general`
  при первом старте падает на `alembic upgrade head` и лечится повторным
  `docker compose up -d general`.
* **Пары брать из `watched_pair` восстановленной базы,** а не пересобирать
  скринером: `./run.sh init` сменит состав пар и обнулит сопоставимость с
  накопленным (раздел 1, «Две ловушки»).
* **Признаки и сделки окажутся в разных базах.** Локально копятся спред и
  стакан, а сделки парка появятся на сервере, когда его поднимут. Для
  офлайн-счёта это неважно. Но шаг «запись признаков без гейта» требует,
  чтобы дельта и OBI лежали в том Redis, из которого читает симулятор, —
  значит локальный сбор это стенд для 5.1 и обкатка самого воркера, а не
  замена питателю на сервере. Когда парк вернётся, воркер едет туда.

### Почему запись раньше гейта

Офлайн-счёт даёт пороги по импульсу и дельте, но не по OBI (5.2), и даёт
их на чужой выборке — месяц истории по тем парам, которые вообще есть на
фьючерсах, без нашей модели исполнения и без наших комиссий на конкретных
объёмах. Поэтому запись признаков (шаг 6) не отменяется офлайн-счётом, а
становится дешевле: проверяется не «какой порог», а «подтверждается ли
посчитанный».

Постановка задания 3 требует сразу гейтить вход по порогам, взятым с
потолка (Relative Delta > 60%, «OBI сдвинут в сторону движения», K сигм).
Мы установили, что сноса во входе нет. Если навесить фильтр с угаданным
порогом и перезапустить парк, через неделю получится **один бит** — стало
лучше или хуже, — на выборке, несопоставимой со старой, и без ответа,
порог виноват или сам признак.

Запись без гейта даёт на тех же сделках условное распределение валового
P/L по каждому признаку. Разработка метрик при этом одинакова в обоих
вариантах, так что ничего не откладывается: меняется только то, что
происходит на шаге 7.

## 6. Что нельзя забыть

`exit_slippage` = ATR × `exit_slippage_atr` в её `open_position`, и

`strategy_0` слова `slippage` нет вовсе. Фактический размер, восстановленный
из данных по 12 347 сделкам, — **0.327 на сделку** при среднем ATR 0.327% и
`exit_slippage_atr` = 0.1, то есть вчетверо больше полспреда (0.077), который
пришлось бы начислить за ту же ногу выхода. Начислять его сверху — двойной
счёт. На парк это влияет на 0.7% поправки, заголовок 0.264 держится.

**Отсюда следствие для раздела 2, которое там не отмечено:** сравнение
«`legacy` +0.03 против `strategy_1` −1.57» ведётся на разных правилах —
одной стратегии начислено проскальзывание, другой ноль. Разрыв между ними
меньше, чем выглядит.

**0.264 — нижняя оценка по глубине книги и верхняя по модели выходов.**
Снизу: на всех 55 парах лучший уровень держит меньше $1000 в медианном
снимке (медиана $76 на худшей стороне) при номинале сделки ровно 1000 —
рыночный ордер съедает несколько уровней. На отдельных мгновениях у 21
пары из 55 лучшая сторона доходила до $1000 и выше, так что это
утверждение про типичное состояние книги, а не про каждый тик. Сверху:
модель считает **все** выходы рыночными, а 29.3% сделок (146 552) закрылись
по тейку, который на бирже вполне может стоять лимиткой. Если считать тейк
maker-ногой, поправка падает до **0.221** (+22% вместо +27%).

Оговорка: замер сделан вечером 2026-09-23, а не в окне прогона. Поэтому
и заведены колонки 7.4 — чтобы следующий замер считался по факту.

### 7.3. Тормоз по BTC: эффекта нет там, где было что мерить

Минутные свечи BTCUSDT из `/fapi/v1/klines` за 22–23 сентября (2532
штуки), join по минуте открытия сделки.

**Порога из постановки не было ни разу на пятиминутном окне.** Максимум
`|ΔBTC_5m|` за все 2532 минуты — **0.894%**; минут выше 1.5% ноль, выше
1.0% тоже ноль. На пятнадцатиминутном окне случаи есть: максимум
**1.63%**, выше 1.5% четыре минуты, выше 1% — четырнадцать. То есть
«за считанные минуты» порог достижим, если мерить не пятиминуткой.

Валовое, очищенное от средних по «пара × стратегия», единица наблюдения —
минута (по правилу раздела 6, а не по сделке). Минуты **не взвешены** по
числу сделок: минута с одной сделкой весит столько же, сколько минута с
пятьюстами, поэтому t в таблице читаются как ориентир, а общее среднее по
минутам −0.066, а не ноль:

| \|ΔBTC_5m\| | минут | сделок | остаток | t |
|---|---|---|---|---|
| < 0.10 | 964 | 364 915 | −0.044 | −0.85 |
| 0.10–0.20 | 236 | 84 281 | −0.092 | −0.86 |
| 0.20–0.30 | 67 | 25 153 | −0.471 | −2.14 |
| 0.30–0.50 | 25 | 12 084 | −0.218 | −0.59 |
| > 0.50 | 12 | 13 544 | **+1.286** | +1.17 |

Зависимость немонотонна, самый бурный бакет — плюс, единственный t за −2
живёт на 67 минутах из 1304 и не переживает поправку на пять сравнений.
Корреляция остатка с `|ΔBTC_5m|` **+0.019**, с `|ΔBTC_1m|` **+0.052**, с
`|ΔBTC_15m|` **−0.021** — все три около нуля, у двух знак противоположен
гипотезе. Знаковая проверка тоже пустая: BUY хуже всего в спокойные
минуты (−0.199), SELL при падении BTC круче −0.3% даёт **+0.760**, лучшая
из десяти ячеек.

### Движение вперёд: то, ради чего тормоз и задумывался

Всё выше смотрит **назад** от момента входа, а содержательная постановка
тормоза — про движение **вперёд**: плохо ли входить прямо перед тем, как
BTC поедет. Проверено отдельно.

Модульная форма (собственно волатильность) пуста и вперёд: корреляция
остатка с `|Δ вперёд 5м|` **+0.031**, бакеты той же немонотонной кашей,
на 3/10/30 минутах ничего.

Знаковая форма вперёд даёт на минуте слабый след одного знака на всех
горизонтах 3–15 минут: `f3` **−0.058** (t −2.08), `f5` −0.050, `f15`
−0.051; со взвешиванием по числу сделок до −0.087 (t −3.14). Читается это
как «BTC растёт в ближайшие минуты → парку хуже».

**Но он не переживает честную единицу наблюдения.** На неперекрывающихся
блоках: 15 минут t −1.42, 30 минут t −0.26, **час — t +1.15 по `f3` и
+1.11 по `f5`, то есть знак переворачивается**. Прореживание по фазе даёт
по `f15` разброс от +0.195 до −0.539: эффект сидит в горстке минут. По
парам — орёл-решка: знак отрицателен у 29 пар из 52, положителен у 23.
Размер и без того не окупает разговора: наклон −1.0 валового на 1%
движения BTC, при sd = 0.124% это −0.12 на сделку на сигму против
комиссии 0.99.

### Чего эта проверка НЕ доказала

Отрицательный ответ здесь узкий, и путать его с «BTC не влияет» нельзя.
Мощность по бакетам (минимально различимый эффект, 80% при α = 0.05):

| \|ΔBTC_5m\| | минут | различимый эффект |
|---|---|---|
| < 0.10 | 964 | **0.15** |
| 0.10–0.20 | 236 | 0.30 |
| 0.20–0.30 | 67 | 0.62 |
| 0.30–0.50 | 25 | 1.04 |
| > 0.50 | 12 | **3.08** |

То есть в спокойных минутах видно эффект вшестеро меньше комиссии — и его
там нет. **А в самом бурном бакете видно только эффект от 3.08 на сделку,
втрое больше комиссии.** Тормоз, который спасал бы 0.5–1.0 на сделку в
бурные минуты, эта проверка **не увидела бы**. Двенадцать минут — не
выборка. По корреляции то же самое: на минуте различимо r от 0.078
(наблюдали +0.019), на часе — только от **0.61**.

**Что отсюда следует.** Строить тормоз сейчас не на чем: там, где данных
много, эффекта нет, а там, где он мог бы быть, данных нет. Это основание
**не начинать разработку**, а не вывод «BTC никогда не важен». Обвала в
окне не было — максимум движения 0.894% за пять минут, — и именно на
обвале тормоз и должен был бы работать.

**Когда переспросить:** после прогона, в котором есть хотя бы один день с
движением BTC на 2–3%. Проверка стоит полчаса и повторяется тем же
способом — скачать `/fapi/v1/klines`, сджойнить по минуте, посчитать
остаток от средних по «пара × стратегия». Порог для решения задать
заранее: эффект в бурных минутах хуже спокойных на величину, сравнимую с
комиссией.

### 7.4. Bid и ask сохраняются

Колонки `best_bid_price`, `best_bid_qty`, `best_ask_price`,
`best_ask_qty` в `AssetHistory`, миграция `c7d4a29f8b15`. Разбор — функция
`book_top` в `general/app/scripts/watch_ws_and_save.py`, она же отдаёт
`BOOK_FIELDS`. Середина спреда как `last_price` не изменилась: правило
входа и выхода не тронуто, сопоставимость цела.

Три вещи, которые неочевидны:

* **набор ключей у записи всегда один и тот же**, даже когда книги нет.
  `AssetHistoryCrud.bulk_create` вставляет пачку одним многострочным
  INSERT, а колонки берутся из первой строки, и разнородная пачка
  ломается двумя разными способами: строка без ключей **первой** —
  вставка проходит, края спреда у остальных молча уходят в NULL; строка
  без ключей **после** строки с ключами — `CompileError`, который
  `save_filtered_assets` ловит своим `except Exception` и откатывает,
  теряя всю пачку котировок. Оба воспроизведены в тесте;
* **перевёрнутую или нулевую книгу отбрасываем целиком**, обе стороны. По
  половине книги считается отрицательный спред, и заметить это потом
  нечем;
* **bid и ask попали и в снимок Redis** (`price_snapshot:*`), рядом с
  ценой. Симулятор читает цену оттуда, а не из БД, так что проверке
  post-only и теневому замеру исполнения нужен именно снимок. Читатели
  разбирают его через `parse_snapshot`, лишние ключи игнорируются.
  **Но пользоваться снимком для post-only можно не в любом режиме:** при
  `MARKET_DATA_SPOT_STREAM=aggTrade` цена берётся из сделки, а bid и ask
  достаются из `@ticker` возрастом до секунды — цена может оказаться вне
  `[bid, ask]`, и проверка ответит неверно. Годится только режим
  `bookTicker`, где всё из одного сообщения.

**Где эти поля берутся.** У фьючерсного `!ticker@arr` (режим `ws`) и у
REST `/fapi/v1/ticker/24hr` полей bid/ask нет вовсе — проверено
подключением, не по памяти. Поэтому заведён отдельный режим
`futures_ws`, см. 7.6; на нём колонки и наполняются. В спотовом режиме
поля тоже приходят — из `bookTicker` и `@ticker`.

Проверка: `python -m tests.test_book_top` — разбор книги, битые и
перевёрнутые варианты, однородность набора ключей, наличие колонок в
модели. Только заглушки.

### 7.5. Сетка прострелов расширена

`WINDOW_SECONDS` получил 1 секунду, `MOVE_PERCENTS` — 2.0%
(`general/app/constants/strategy_0_seed.py`). Было 648 конфигураций,
стало **1080**. Сопоставимость не задета: сделок у стратегии 0 нет ни
одной, парк не заводился.

Заводить парк по-прежнему нельзя без сервера, и мешает не только он: под
`strategy_0` не назначены пары в `strategy_pairs`, а в `strategies` нет
самой строки — там только `legacy` (id 1) и `strategy_1` (id 3).

**Односекундное окно упирается в разрешение фида, и это надо решить до
заведения парка.** Замер живьём на `!ticker@arr`: медианный интервал
между тиками одного символа **1.21 с**. В спотовом режиме снимок
обновляется пачкой раз в `MARKET_DATA_SPOT_FLUSH_SEC` (сейчас 0.5 с).
Скользящее окно в `wait_for_entry` при `POLL_SECONDS` = 0.1 наберёт за
секунду десяток отсчётов, но различных цен среди них одна-две — то есть
односекундное окно меряет «дельту между двумя соседними тиками», а не
движение за секунду. Вдобавок фьючерсная `c` из `!ticker@arr` — агрегат
24-часового тикера, внутрисекундный прострел в неё не попадает в
принципе.

Практически: на прежнем фиде 216 конфигураций с окном 1 с дублировали бы
окно 2 с. **Поэтому источник переведён на тиковый — раздел 7.6**, и это
условие снято: цена в Redis обновляется раз в 50 мс, стратегия опрашивает
раз в 100 мс. Осталось помнить, что на `MARKET_DATA_SOURCE=ws` эти
конфигурации соберут шум, а также что в сетке окон 1/2/5/10/30 нет 3
секунд, хотя «1–3 секунды» цитируется дословно.

### 7.6. Поток котировок переведён на фьючерсный `@bookTicker`

Режим `MARKET_DATA_SOURCE=futures_ws`, функция
`run_futures_ws_listener` в `general/app/scripts/watch_ws_and_save.py`.
Включён в `general/.env`.

**Зачем.** Прежний `!ticker@arr` отдаёт снимок 24-часового тикера
примерно раз в секунду и **не содержит bid/ask вовсе**. На нём нельзя ни
померить спред по факту, ни проверить post-only, ни разглядеть прострел
короче секунды — то есть три задачи сразу упирались в источник, а не в
логику.

**Два соединения, а не одно.** Фьючерсные потоки разнесены Binance по
базовым URL: `@bookTicker` живёт на `/public`, `@ticker` — на `/market`.
Замер 2026-09-23: при смешанной подписке на `/public` приходят **только**
`bookTicker`, а `@ticker` молча проглатывается. Это ровно тот отказ, что
описан в пункте 29 [08-gotchas.md](08-gotchas.md) — подписка принята,
данных нет. Поэтому два сокета со своим переподключением у каждого:
падение одного не роняет второй.

**Redis и база живут на разных частотах — это главное решение.**

| | частота | почему так |
|---|---|---|
| приходит с биржи | **834 тика/с** на 55 парах | замер 2026-09-23, медиана 3.2 тика/с на пару, максимум 256 (PTBUSDT) |
| публикация в Redis | раз в **0.05 с** на пару | столько же, сколько `PriceCache.REFRESH_INTERVAL_SECONDS`; чаще бессмысленно — в ключе живёт одно значение, монотонность отбросит промежуточные |
| запись в `asset_history` | раз в **1 с** на пару | запись каждого тика — 72 млн строк в сутки, чего не выдержит ни диск, ни ретеншн |

Секундная плотность истории выбрана не наугад: ровно столько давал
`!ticker@arr`, поэтому ни статистика волатильности (`MIN_TICKS_IN_WINDOW`
и соседние в `general/app/constants/volatility.py`), ни диск подмены не
замечают. Новое в строке — только bid, ask и их объёмы.

**`last_price` остался серединой спреда.** Края кладутся рядом, а не
вместо: по середине посчитаны все накопленные сделки, и подмена обнулила
бы сопоставимость. Логика входа и выхода не тронута.

**Как разделились обязанности.** `save_filtered_assets` получила
параметр `publish`. Фьючерсный слушатель публикует сам, раз в 50 мс, а
историю пишет раз в секунду с `publish=False`: повторная публикация того
же события вернула бы «не принято» (срок и монотонность считаются по
времени события), и записи молча отфильтровались бы — история осталась
бы пустой. Правило «в историю идут только принятые события» (пункт 25
[08-gotchas.md](08-gotchas.md)) при этом соблюдено: слушатель сам
отбирает по флагам от `publish_prices`.

**Проверено вживую** на 55 watched-парах: 38 строк в секунду, у всех
заполнена книга, `ask > bid` во всех, средний спред **0.0276%** — сходится
с REST-замером 7.2 (медиана 0.0293%, повторный 0.0273%). Снимки в Redis
несут `bid` и `ask` рядом с ценой.

**Чего это не делает.** Стакан глубже первого уровня (задание 2),
`aggTrade` и дельта (задание 1) — по-прежнему нет. Приватный поток
`user_data_websocket_client.py` до сих пор ходит на старый путь
`fstream.binance.com/ws/{listenKey}`, хотя пункт 29 говорит, что
listenKey переехал на `/private`. Боевой бот выключен, поэтому это пока
не жжёт, но при его включении будет тот же тихий отказ.

### 8.2. Выгрузка: `fetch_binance_history.py`

Скрипт `general/app/scripts/fetch_binance_history.py`, запускается
руками, в `supervisord.conf` не заведён.

```bash

BINANCE_HISTORY_DIR=~/binance-history python3 -m app.scripts.fetch_binance_history
BINANCE_HISTORY_DIR=~/binance-history python3 -m app.scripts.fetch_binance_history --download
```

это гигабайты, и решение качать принимает человек. Сверх того есть
потолок `--max-gb` (по умолчанию 40), выше которого скрипт отказывается
качать даже с `--download`.

**Запускается с хоста, а не из контейнера** — каталог выгрузки лежит вне
контейнера. Отсюда два решения в коде, оба намеренные:

* **без `app.db.base`** (он тянет `redis`, которого на хосте нет) и

  лежит `REDIS_PORT` для подстановки в `docker-compose.yml`. Адрес базы
  поэтому свой аргумент — `--db-url`, по умолчанию `DEFAULT_DB_URL`,
  опубликованный порт Postgres, а не имя сервиса `db`;
* зависимости — только `httpx` и `sqlalchemy`, оба на хосте есть.

**Питатель котировок падал раз в сорок секунд — починено.** При
подключённом слушателе стакана `symbols_history` стал вылетать с
`redis.exceptions.ConnectionError: Connection closed by server` и
подниматься супервизором заново: девять перезапусков за семь минут.

Причина не в Binance и не в стакане. `RedisSessionManager` в
`general/app/db/base.py` отдаёт клиента через `Redis.from_pool`, а тот
по документации redis-py «takes ownership of the connection pool and
closes it when the Redis client is closed». Пул при этом **общий** —
singleton по адресу. В `run_futures_ws_listener` два потребителя:
`publisher` раз в 50 мс и `historian` раз в секунду, и каждый входил в
свой `redis_context()`. Выход публикации из контекста рвал пул под
работающим `pipe.execute()` историка.

Правка узкая: один Redis на весь процесс, открытый вокруг `asyncio.gather`
в `run_futures_ws_listener`, и так же в `run_order_book_listener`.
Логика не менялась, сопоставимость не затронута.

Эффект замерен на самой базе: **22.6 строки в секунду до правки, 37.5
после** — то есть терялась почти треть котировок. За четыре минуты
наблюдения после правки ноль `Traceback` и непрерывный аптайм.

Мина общая, а не только у этих двух питателей: **любой процесс, где два
корутина независимо входят в `redis_context()`, воспроизведёт то же
самое.** Чинить это в самом `RedisSessionManager` (не `from_pool`, а
`Redis(connection_pool=...)`, чтобы выход из контекста не рвал пул) —
отдельная правка, она трогает и симулятор, и воркеры, и делать её ночью
под сбором данных незачем.

**Спред пишется**, проверено на свежих строках: 55 пар, `best_bid_price`
и `best_ask_price` заполнены, `ask > bid` во всех. Средний спред за
первую минуту сбора — от **0.0036%** (`VVVUSDT`) до **0.1377%**
(`ALCHUSDT`), то есть разброс по парам почти **сорокакратный**. Это само
по себе довод считать порог по каждой паре, а не один на всех: барьер

второе слагаемое вчетверо больше, чем на `VVVUSDT`.

Плотность по парам: медиана 554 строки из 605 возможных — почти все пары

**OBI считается.** `order_book_imbalance` в
`order_book_listener.py`, по `ALGOUSDT` за эти десять минут (516 строк):

| Глубина | p10 | медиана | p90 |
|---|---|---|---|
| 1 уровень | −0.747 | +0.083 | +0.748 |
| 5 уровней | −0.284 | +0.040 | +0.382 |
| 20 уровней | −0.114 | −0.020 | +0.170 |

**Это главный результат сбора, и он методологический.** Распределение
OBI целиком определяется глубиной, по которой он посчитан. Порог «OBI
сдвинут в сторону движения» из постановки задания 3 без указания глубины
не задаёт ничего: «OBI > 0.3» на первом уровне срабатывает чаще чем в
четверти случаев, а на двадцати — почти никогда. **Глубина — такой же
параметр сетки, как окно и порог движения**, и подбирать её придётся
вместе с ними.

Ровно поэтому `order_book_imbalance` принимает `levels` аргументом и
возвращает `None`, когда считать не по чему: ноль в этом месте соврал бы
«равновесие» там, где данных нет.

### 8.10. Что осталось и обо что можно споткнуться

* **Очередной шаг — офлайн-счёт (5.1, пункт 2 списка).** Данные под него
  лежат, разреженность секундной сетки (8.3) и глубина OBI (8.7) — два
  входных параметра, которые теперь известны заранее.
* **Слушатель локально запускали от uid 1000** (`docker exec -u
  1000:1000`), чтобы файлы архива остались за пользователем хоста. Под
  supervisord он пойдёт от root, и файлы будут root-овы. На сервере это
  безразлично, на ноутбуке — заметно.
* **`docker exec` с `timeout` оставляет процесс в контейнере.** Убивается
  клиент, а не питон внутри. На этом сборе два забытых слушателя
  дописывали в те же gzip-файлы, и замер пришлось выбросить и повторить:
  три процесса в один `.gz` через `O_APPEND` дают нечитаемое месиво.
  Останавливать надо `pkill -TERM` **внутри** контейнера — тогда
  отрабатывает штатное закрытие архива.
* **`order_book` заведён с `autostart=false`.** Если контейнер
  перезапустится, сбор стакана молча не возобновится, а
  `rebuild_watched_pairs` (у него `autostart=true`) вернётся и через
  сутки после старта сменит состав пар. При долгом сборе проверять
  `supervisorctl status` после каждого перезапуска контейнера.
* **`RETENTION_ASSET_HISTORY_HOURS` остался 24 часа.** Стакан лежит в
  файлах и переживёт что угодно, а **спред живёт только в
  `asset_history`** и старше суток не бывает. Для сбора спреда длиннее
  суток придётся либо поднимать срок (цена — в 8.5), либо складывать
  края книги в файлы тем же приёмом, что и стакан.
* **`user_data_websocket_client.py` всё ещё на старом пути** (пункт 29,
  раздел 7.6). Не тронут, боевой бот выключен.

**Вывод: и потолок скорости, и частота обрывов считаются на
соединение, а не на стрим.** На плохом канале одно соединение упирается
примерно в 20 сообщений в секунду **независимо от того, сколько на нём
стримов**, и живёт 25–50 секунд. Те же стримы, разложенные по отдельным
сокетам, идут на полной скорости и не рвутся.

Канал при этом плохой сам по себе: машина сидит на **Wi-Fi** (Ethernet
отключён), джиттер наружу 21–208 мс при среднем 57. Пропускная
способность в порядке — архив с data.binance.vision качается на
4.5 МБ/с. То есть режется не полоса, а именно долгоживущее соединение.

**Но качество канала тут ни при чём — проверено.** В 12:00 того же дня,
когда джиттер упал до 19–41 мс (mdev 10 против 56), замер повторили на
тех же 55 парах:

| | фреймов/с | КБ/с |
|---|---|---|
| все 55 стримов в одном сокете | **16** | 16.6 |
| те же 55 по пяти (11 сокетов) | **171** | 175.7 |

Один сокет отдаёт те же ~16–20 сообщений в секунду и на хорошем канале,
и на плохом. Значит потолок не про джиттер и не про Wi-Fi, а про само
соединение, и раскладка по сокетам нужна всегда, а не только пока сеть
плохая. Почему вечером 2026-09-23 один сокет отдавал 250 фреймов в
секунду, а с полуночи перестал, — не выяснено; похоже на то, что Binance
начал считать лимит по соединению для этого IP.

**Правка.** `split_streams` в обоих сборщиках, по
`ORDER_BOOK_STREAMS_PER_SOCKET` = 5 стримов на сокет: 11 сокетов у
стакана, 11 + 11 у питателя (`@bookTicker` и `@ticker` живут на разных
базовых URL). Ноль в настройке означает прежнее поведение — все стримы
одним сокетом.

Замер сразу после правки, тот же канал, те же пары:

| | было | стало |
|---|---|---|
| Фреймов в секунду | 20 | **210** |
| Обрывов за 4 минуты | 9 | 3 |
| Строк в архив в минуту | ~900 | ~2250 |

**Вторая правка — цена обрыва.** В `finally` стояло фиксированное
`asyncio.sleep(3)` на каждый обрыв. За ночь это 877 × 3 с = 44 минуты
сна у стакана и 47 у питателя. Заменено на паузу, которая растёт только
после соединений, умерших сразу: `RECONNECT_MIN_SEC` 0.5 с,
`RECONNECT_MAX_SEC` 8 с, удачным считается соединение, прожившее дольше
`RECONNECT_HEALTHY_SEC` = 15 с.

**Чего это не чинит.** Обрывы не исчезли, их стало меньше. Пока сбор
идёт по Wi-Fi, часть данных будет теряться; провод или сервер уберут
проблему совсем. Для офлайн-счёта по архивам это безразлично — там
дампы, — но пороги по OBI считать по такой выборке надо с оглядкой на
дыры.

**Что это значит для сервера.** Раскладку по сокетам везти туда же:
потолок держится независимо от качества канала, и рассчитывать на то,
что на сервере одно соединение потянет все 55 стримов, оснований нет —
первое, что стоит померить после переезда, это те же две строки таблицы
выше. Настройка оставлена настройкой, а не константой, ровно поэтому:
`ORDER_BOOK_STREAMS_PER_SOCKET = 0` возвращает прежнее поведение одним
сокетом, если окажется, что там потолка нет.

Бэктестера, как и договаривались, нет: ни матчинга, ни очереди в книге.
Считается условное распределение движения вперёд после срабатывания
триггера плюс MFE и MAE — путь цены, а не исполнение.

### 9.1. Как считалось

Триггер повторяет `wait_for_entry` из `strategy_0/algorithm.py`:
скользящее окно, сравнение самой старой цены в окне с текущей, вход при
`|change| >= move_percent`. Сетка — `WINDOW_SECONDS` и `MOVE_PERCENTS`
из `strategy_0_seed.py`, чтобы считать ровно то, что будет исполнять
парк. Шаг сетки — `POLL_SECONDS` = 100 мс, как у бота.

Три поправки, каждая меняет ответ:

* **отсчёт от цены через `ENTRY_LAG_MS` = 150 мс,** а не от цены
  триггера;
* **издержки по своим ставкам:** комиссия 0.1% за круг плюс замеренный
  спред 0.0264% = барьер **0.1264%**;
* **события не перекрываются** — следующее не ближе
  `EVENT_COOLDOWN_SECONDS` = 180 с, иначе выборка зависимая.

### 9.2. Главный результат: вход по движению не работает

`entry_mode = continuation` — **отрицательная медиана во всех двадцати
ячейках сетки** «окно × движение», на 1 150 558 событиях. На движениях
0.3% и 0.5% положительной медианы нет **ни у одной из 53 пар**.

| окно, с | 0.3% | 0.5% | 1.0% | 2.0% |
|---|---|---|---|---|
| 1 | −0.162 | −0.187 | −0.280 | −0.455 |
| 5 | −0.159 | −0.182 | −0.251 | −0.399 |
| 30 | −0.151 | −0.167 | −0.204 | −0.274 |

(медиана чистого P/L за круг, %, горизонт 30 с, взвешено по событиям)

Чем крупнее прострел, тем хуже: к моменту, когда движение видно, его уже
разобрали. Это тот же вывод, что дал парк в разделе 2, но теперь на
миллионе событий и на месяце истории, а не на сутках.

**Для сетки это означает:** половина из 1080 конфигураций
(`entry_mode = continuation`) проверяется ради контроля, а не ради
надежды.

### 9.3. Вход против движения: медиана врёт, среднее спасает

`entry_mode = reversal` даёт положительную медиану на крупных движениях,
и доверительный интервал медианы уверенно исключает ноль. Но:

| окно / горизонт | n | медиана | **среднее** | дов. интервал среднего |
|---|---|---|---|---|
| 1 с / 30 с | 1468 | +0.186 | **−0.002** | [−0.122; +0.120] |
| 1 с / 60 с | 1468 | +0.370 | **−0.018** | [−0.179; +0.144] |
| 1 с / 180 с | 1468 | +0.570 | **+0.255** | [+0.060; +0.446] |
| 5 с / 180 с | 2565 | +0.431 | +0.049 | [−0.084; +0.185] |

(движение 2.0%, объединённо по парам, bootstrap 4000)

**Медиана положительная, а среднее нулевое или отрицательное.** 56–60%
мелких выигрышей против 40–44% крупных проигрышей: худшие события в
выборке — −29%, −27%, −26%. Правило с медианой +0.37% и средним −0.02%
разоряет.

Это зеркало того предупреждения, что записано в 5.1 («смотреть медиану,
а не среднее»). Оно верно, но недостаточно: **смотреть надо на обе
величины**, потому что ловушки две и они разного знака. В счётчике
поэтому считаются и медиана, и среднее, и обрезанное среднее, и
bootstrap-интервал.

Единственная ячейка, где среднее уверенно больше нуля, — **вход против
движения 2% за 1 секунду, удержание 180 секунд**: +0.255%, интервал
[+0.060; +0.446], 1468 событий. Без десяти лучших событий среднее всё
ещё +0.158%, то есть это не пара выбросов.

### 9.4. «Гейт по дельте» оказался асимметрией выброса

Первый счёт показал: события, где дельта согласна со стороной входа,
дают среднее втрое выше. Проверка убила вывод — **знак дельты в окне
совпадает со знаком самого движения в 97% событий**. Дельта, посчитанная
в том же окне, которое движение и создало, не признак, а тот же импульс
под другим именем.

Что там на самом деле — асимметрия направления:

| правило | выброс ВВЕРХ (шортим) | выброс ВНИЗ (лонгуем) |
|---|---|---|
| 1.0% / 30 с | +0.010 [−0.03; +0.06] | **−0.229 [−0.28; −0.18]** |
| 1.0% / 180 с | +0.069 [−0.02; +0.16] | **−0.142 [−0.23; −0.05]** |
| 2.0% / 30 с | **+0.268 [+0.11; +0.42]** | **−0.247 [−0.43; −0.06]** |

**Покупать быстрый провал — устойчиво убыточно** (3340 событий, интервал
исключает ноль на обоих горизонтах). Шортить быстрый выброс вверх —
около нуля на 1% и заметно в плюсе на 2%, но там всего 699 событий.

Нынешняя сетка эту асимметрию **выразить не может**: `entry_mode`
симметричен по построению. Это отдельный параметр, которого в
`Strategy0Config` нет.

### 9.5. Уровни выхода не совпадают с масштабом сделки

На выжившей ячейке (2% за 1 с, горизонт 180 с):

* MFE: медиана **1.78%**, p25 0.88, p75 3.18
* MAE: медиана **1.29%**, p25 0.39, p75 3.31

Сетка `TAKE_PERCENTS` и `STOP_PERCENTS` — 0.2 / 0.4 / 0.8%. Сколько
сделок такой стоп выбивает до того, как цена дойдёт куда-нибудь:

| стоп | выбито сделок |
|---|---|
| 0.2% | 83% |
| 0.4% | 75% |
| 0.8% | 60% |
| 1.5% | 46% |
| 3.0% | 27% |

**Сетка не умеет выразить ту сделку, которая единственная выжила.** При
стопе 0.8% три сделки из пяти закроются шумом, не дойдя ни до цели, ни до
таймаута. Правки в `strategy_0_seed.py` я не вносил — это отдельный шаг
плана и отдельное решение, — но без расширения `STOP_PERCENTS` вверх
(1.5–3%) проверять шаг 9.3 бессмысленно.

### 9.6. Задержка в 150 мс съедает половину барьера

Медиана движения, ушедшего между решением и заявкой:

| окно | 0.3% | 1.0% | 2.0% |
|---|---|---|---|
| 1 с | −0.001 | −0.065 | **−0.077** |
| 5 с | −0.000 | −0.025 | −0.061 |
| 30 с | 0.000 | −0.002 | −0.024 |

На движении 2% за секунду задержка стоит **0.077% из барьера 0.1264%** —
больше половины. На движении 0.3% она не стоит ничего. Это прямое
следствие того, о чём предупреждал раздел 5.1, и цифра теперь есть.

### 9.7. Таблицы «символ → порог» не будет

Задумывалось получить пороги **по каждой паре**. Считать их не по чему:
на движении 2% медиана событий на пару — **11 штук за месяц**, а медианы
по парам разбросаны от −4.26% (`VVVUSDT`) до +4.13% (`CUSDT`). Это
разброс одиннадцати наблюдений из распределения с децилями ±3.6%, то
есть шум, а не характер пары.

Любой отбор пар по этим числам — отбор по шуму, и он воспроизведёт
ровно ту ошибку, от которой предостерегает
[.ai/rules/experiments.md](../../rules/experiments.md): метрика, которая
появляется только после выбора, выбором управлять не может.

**Пороги считаются на парк целиком, а не на пару.** Чтобы говорить о
паре, нужен либо год истории, либо пары с событиями на два порядка чаще.

### 9.8. Что из этого следует для сетки

Предложение, не правка — `strategy_0_seed.py` не тронут:

| Параметр | Сейчас | Предложение | Почему |
|---|---|---|---|
| `entry_mode` | continuation, reversal | оставить обе, но парк по continuation держать контрольным | 9.2: убыточен на 1.15 млн событий |
| `move_percent` | 0.3 / 0.5 / 1.0 / 2.0 | **1.0 / 2.0 / 3.0** | 0.3 и 0.5 отрицательны в обоих режимах везде |
| `window_seconds` | 1 / 2 / 5 / 10 / 30 | **1 / 2 / 5** | 10 и 30 гасят эффект |
| `max_hold_seconds` | 30 / 60 / 180 | **180 / 300** | среднее выходит в плюс только к 180 с |
| `stop_loss_percent` | 0.2 / 0.4 / 0.8 | **+ 1.5 / 3.0** | 9.5: 0.8% выбивает 60% сделок шумом |
| `take_profit_percent` | 0.2 / 0.4 / 0.8 | **+ 1.5 / 2.5** | MFE медиана 1.78% |
| направление выброса | нет такого параметра | **добавить** | 9.4: вверх и вниз ведут себя по-разному |

Сетка при этом не разрастается: 3 × 3 × 2 × 5 × 5 × 2 — но большая её
часть уходит на выход, а не на вход, и это правильный размен: вход
посчитан, выход — нет.

### 9.9. Чему верить нельзя

* **Месяц — один режим рынка.** Август 2026 без обвала. Вывод 9.2
  (continuation убыточен) устойчив на миллионе событий, вывод 9.3 (плюс
  на 2% за 1 с) держится на 1468 событиях и одном месяце.
* **`aggTrades` — цены сделок, бот видит середину спреда.** Разница до
  половины спреда учтена как издержка, но не как шум цены.
* **Проскальзывание сверх спреда не моделируется вовсе.** На паре,
  которая только что прошла 2% за секунду, книга тонкая; реальный вход
  будет хуже расчётного, и часть от +0.255% съест именно он.
* **Пары отобраны скринером по скачкам волатильности.** Проверять на них
  стратегию, которая живёт на скачках, — смещение, о котором надо
  помнить.

(среднее чистого P/L, %, объединённо по парам, bootstrap)

**Покупать быстрый провал — самый надёжно измеренный убыток всего

импульс под другим именем.

### 10.5. Из 1080 конфигураций данные поддерживают одну семью

Шортить выброс **≥2% за 1–2 секунды, держать 30 секунд**. Всё остальное
либо убыточно, либо неотличимо от нуля.

Сетка этого не выражает: `entry_mode` симметричен, а стопы 0.2–0.8%
выбивают 60–83% сделок шумом (9.5). Правок в `strategy_0_seed.py` нет —
предложение в 9.8 остаётся в силе, с одной поправкой: `max_hold_seconds`
= 30 теперь выглядит не хуже 180, а на 2% даже лучше по среднему.

### 10.6. Открытый вопрос, ради которого идёт локальный сбор

Разница между шортом выброса (+0.178%) и лонгом провала (−0.487%) —
**две трети процента на движениях одинаковой величины**. Объяснения нет.

Естественный кандидат — состояние книги: выброс вверх на тонком аске и
каскад ликвидаций вниз в стакане выглядят по-разному. Проверить можно
только своим сбором, в дампах книги нет (5.2).

Поэтому сбор расширен с 55 пар на все 570 (`ORDER_BOOK_SYMBOLS=all`,
`@depth20@500ms`, 57 сокетов). Прострелов 2% за секунду на 55 парах
около 47 в сутки, на 570 — примерно 490, и полторы тысячи событий со
стаканом набираются за трое суток вместо месяца.

Если асимметрия объяснится книгой — из неё получается признак входа.
Если нет — значит это свойство выборки, и опираться на неё нельзя. Оба
ответа закрывают вопрос.

## 12. Смена приоритетов, 2026-09-27

Решение трейдера по итогам раздела 11: **торговля по рынку (тейкером) на
признаках только из истории сделок исключается из планов.** Это

### 12.1. Приоритет 1 — стратегия 1 (Squeeze Grid), мейкерское исполнение

Вход лимитной заявкой: издержки ниже, чем у тейкера, и спред не
платится на входе. Задача — довести до запуска парк `strategy_1` на
утверждённых восьми парах: **BTCUSDT, ETHUSDT, SOLUSDT, DOGEUSDT,
1000PEPEUSDT, SUIUSDT, NEARUSDT, AVAXUSDT**.

> **Поправка того же дня** (раздел 13): мейджоры сняты — у них цель
> меньше комиссии, пары остаются прежние восемь альтов скринера. Перед
> перезапуском парка отступ пересчитан на истории — положительного
> матожидания нет ни на одной конфигурации (13.2). Запуск не делается.

Три факта из уже накопленного, с которыми этот пункт надо сверить
**до** заведения парка, — они не отменяют решения, но меняют ожидания:

* **Набор пар расходится с нынешним.** В базе `strategy_1` заведена на
  восьми парах скринера (`ACEUSDT`, `ALGOUSDT`, `BRUSDT`, `CUSDT`,
  `PIEVERSEUSDT`, `SAGAUSDT`, `VVVUSDT`, `牛来USDT`, 1944 бота), и
  [14-strategy-1-squeeze-grid.md](14-strategy-1-squeeze-grid.md), раздел
  «Метрики и почему именно они», прямо отсекает мейджоры: у BTC и ETH при
  ATR 0.03–0.04% цель сделки (`take_profit_fraction × entry_offset_atr ×
  ATR`) **меньше комиссии**, и отсечка `edge_ratio` их не пропускает.
  Смена пар — новый эксперимент, накопленное по старым с ним не
  складывается ([../../rules/experiments.md](../../rules/experiments.md)).
  Сетку отступов в ATR (`ENTRY_OFFSETS_ATR` в
  `general/app/constants/strategy_1_seed.py`) под мейджоры надо
  пересчитать, иначе цель не перекроет издержки ни на одной конфигурации.
* **Экономия — не на порядок.** `COMMISSION_OPEN` и `COMMISSION_CLOSE` —
  по 0.05% (тейкер), ставка maker 0.02%. У `strategy_1` мейкерский только
  вход, **все выходы рыночные, включая цель** (докстринг
  `strategy_1/algorithm.py`, `entry_is_maker`): круг 0.07% против 0.10%
  тейкерского, в 1.4 раза дешевле, плюс полспреда на входе. Полностью
  мейкерский круг — 0.04%, в 2.5 раза, — требует выхода по цели
  лимиткой, а это правка логики выхода и новая точка отсчёта статистики.
* **Первый прогон `strategy_1` был худшим в парке:** валовое −1.57 на
  сделку, самый воспроизводимый эффект выборки (раздел 2). Оговорка из
  7.2: ей одной начислялось проскальзывание выхода, так что разрыв с
  `legacy` меньше, чем выглядит, — но плюса не было и без неё.

### 12.2. Приоритет 2 — поток ордеров по стакану (depth20)

Исследование переносится с `aggTrades` на собственный архив стакана
`@depth20` (`order_book_listener.py`, раздел 8.5). Искать преимущество не
в факте изменения цены, а в **дисбалансе книги — OBI на 5 и 10
уровнях** (`order_book_imbalance`, аргумент `levels`) — в сочетании со
**всплесками тикового объёма и CVD**.

Что есть и чего не хватает:

* **Архива мало.** Лежит в `order_book/` каталога выгрузки: 55 пар за
  2026-09-23, 570 пар за 2026-09-24 и 2026-09-25 (до 16:49 UTC), 1.7 ГБ.
  Около полутора суток. Слушатель `order_book` в supervisord сейчас
  **STOPPED** — первым шагом его поднять и копить.
* **CVD к стакану надо брать за те же сутки.** Августовские `aggTrades`
  с сентябрьским стаканом не совмещаются; сентябрьские дни выгружаются
  тем же `fetch_binance_history.py`.
* **Глубина — параметр, а не константа** (8.7): распределение OBI
  целиком определяется числом уровней, поэтому L5 и L10 считаются
  параллельно, а пороги подбираются на каждой глубине отдельно.
* **Признак берётся до движения, не в его окне.** Урок 9.4: дельта в том
  окне, которое движение создало, совпадает с ним по знаку в 97% случаев
  и признаком не является. OBI и CVD меряются на интервале **перед**
  входом, отсчёт хода — после.
* **Мерить исход по мейкерской модели.** Раз тейкерский вход исключён,
  признак проверяется на том, исполнилась бы лимитка и что было дальше,
  а не на ходе цены от триггера.
* Открытый вопрос 10.6 (асимметрия выброса вверх и провала вниз)
  остаётся первым кандидатом на проверку — ради него сбор и расширяли до
  570 пар.

### 15.5. Точность всплеска объёма: правило записано до счёта

Вопрос: какая доля всплесков кончается сквизом и что делает цена после.
Счёт только по `aggTrades`, поэтому на **всех** парах 24 дней (10 381 день
пар), а не на отобранных по сквизам — иначе точность завышена отбором.

* Сигнал: объём за 500 мс ≥ K × средний 500-мс объём предыдущих 5 минут
  и не меньше N сделок в окне; K ∈ {2, 3, 5, 10, 20}, N ∈ {1, 3, 10};
  повтор на паре не раньше 30 с.
* «Кончился сквизом»: ход ≥1.5% (≥2%) за ≤2 с сработал в пределах 3.5 с
  после сигнала. База — та же доля у всех моментов тех же дней пар.
* Ход: вход через 200 мс по последней сделке в сторону CVD окна, выход
  через 5, 30, 180 с, нетто при 0.15% за круг.
* Подбор — нечётные месяцы (11.2024, 01, 03, 05, 07, 09.2025, 11.2025,
  01, 03, 05, 07, 09.2026), проверка — чётные.

Правило выбора: на подборе берётся конфигурация с наибольшим нетто на
30 с среди тех, где сигналов не меньше 500. Проверка пройдена, если на
чётных месяцах у **этой** конфигурации нетто на 30 с больше нуля и
t по дням больше 2. Отдельно по точности: конфигурация с наибольшей
долей сквизов ≥1.5% на подборе (сигналов ≥ 500) должна на проверке
держать ту же долю не ниже чем вдвое выше базовой.

| сентябрь | вселенная, с фильтром | 3423 | −0.173 | −0.323 | [−0.409; −0.227] | −6.21 |
| сентябрь | топ-100, фильтр, ≤2 позиций | 1722 | −0.096 | −0.246 | [−0.356; −0.136] | −4.05 |

Полные таблицы — `analysis/exhaustion_squeeze_2026-0{8,9}.csv`.

* **Фильтр ничего не отбирает.** Пройден в 100% сквизов, медиана
  ожидания 100 мс, в 43–45% случаев условие выполнено уже на такте
  импульса. Пик приходится на один такт, соседний почти всегда тише
  втрое, а пустой такт (нет сделок) проходит автоматически. Результат с
  фильтром на 0.01–0.02 хуже, чем без него: вход чуть позже, по уже
  откатившейся цене.
* Сентябрь в минусе во всех срезах, валовыми тоже: правило ТЗ повторяет
  вывод 14.3. Отбор по ликвидности и лимит позиций знак не меняют.
* Числа с 14.3 не совпадают (август 4581 события против 3506): там
  выбросы вверх и провалы вниз делили один кулдаун, а здесь считаются
  только выбросы вверх и кулдаун отсчитывается от выхода.

**Итог:** боевой бот по ТЗ не писать — на сентябре он убыточен с
фильтром и без. Технические ошибки ТЗ (несуществующий поток
`!<arr>@aggTrade`, `floor(100 / price)` вместо округления до
`stepSize`, повтор рыночного закрытия без `reduceOnly` и проверки
статуса) переданы трейдеру отдельно.

## 18. Лонг провала на четырёх месяцах с фильтрами портфеля. Исследование закрыто, 2026-10-09

Трейдер попросил сплошной прогон ячейки 14.3 за июнь–сентябрь с

### 18.1. Данные

* июнь и июль — `data/binance/aggtrades` в корне репозитория (в git не
  входит, см. `.gitignore`): 33 941 архив, у каждого официальный
  `.CHECKSUM`;
* август и сентябрь — `BINANCE_HISTORY_DIR`. Перед счётом прогнаны через
  `fetch_binance_history.py --download` по объединённому списку пар
  (оба каталога и все текущие контракты, 702 символа): каждый лежащий
  архив сверен по SHA-256, недостающие докачаны — 137 за август и 2 372

  сколько в бакете; сбоев нет;
* 31 мая (566 архивов) — только ради объёма для фильтра 1 июня.

### 18.2. Правило и как читались неоднозначные места

`dip_long_oos.py`, параметры — константы модуля, в аргументах их нет:

* провал ≥2.0% за ≤1 с, рыночный лонг через 200 мс по последней сделке,
  выход строго через 180 с, издержки 0.15% за круг;
* **топ-100 по обороту в USDT и оборот > $20M** — по **предыдущим**
  UTC-суткам: оборот дня сигнала включает сам каскад. Допущено 60–100
  пар в день, медиана 92;
* **кулдаун 180 с на пару** — от взятой сделки; сигнал, пропущенный из-за
  лимита, кулдаун не запускает;
* **не больше 2 открытых позиций на весь портфель**, слот занят от
  сигнала до выхода. При одновременных сигналах (такт 100 мс) первыми —
  ликвидные по обороту прошлых суток (`select_trades`);
* сигналы, выход которых не помещается в сутки, отброшены, как в
  `squeeze_express`;
* ДИ и t — ошибка среднего по сделкам с кластеризацией по календарным
  дням (CR1, Стьюдент с G−1), `clustered_stats`.
